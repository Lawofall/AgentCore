# 成本、配额与计费

> **状态**：目标形态 = §〇·六 `billing_mode=platform` 全量代付 + `quota_*`（默认 **¥5/月 · ¥5/日 · 500 请求/日**）。**现网可临时 `BILLING_MODE=byok`**（平台代付休眠、无 Key → 402；再开 = 改回 `platform` 重启 api）→ **运维步骤见 §〇·七**。**dev 默认仍 `byok`**。台账权威 = **整数 nano-CNY**（1 元 = 10⁹；无 FX、无 `cny_per_usd`）。无独立「免费档」路径。计费记账 + 配额 + 限流 ✅。

>

## 〇、为什么成本是产品而非基建

AgentCore 是 multi-agent，一条用户消息 = CEO + N 个委派 worker，**花销天然能按 Agent/角色拆开**——这是单 Agent 竞品（Cursor/Codex/Claude）做不到的「团队工资单」。别人只能说「这次花了 ¥X」；AgentCore 能说「CEO ¥0.03 / 调研员 ¥0.05 / 写作 ¥0.04」。所以用量可观测是**产品差异点**，台账的 per-run 聚合视图（由 per-call 明细推导）正是为这个差异点服务。（✅ run 级 ¥ 可拆（`agent_id`）；✅ 人设级拆账：明细/聚合行携带 `persona`/`role`，**单回合**工资单与 `cost.recorded` 的 `by_role` 按角色呈现；账户仪表盘只给窗口总额 / 额度 / 趋势，**不再**做月维度按角色看板。）

## 〇·五、计费模式：部署开关 + per-turn origin

**两档部署形态**（`config.billing_mode`）：

| 形态 | 谁付钱 | 无 Key / 无平台凭据 | 配额 |
|---|---|---|---|
| `byok`（dev 默认） | 用户自带上游 | **402 `LLM_KEY_REQUIRED`** | 有 key 的 BYOK 回合**不查**配额 |
| `platform`（生产目标） | 平台代付；BYOK 为高级选项 | 平台凭据缺失 → 503；用户可自备 key 走 BYOK | 平台路径过 `quota_*`（¥5/月·¥5/日·500 请求/日） |

用户侧不预选「模型来源」：聊天框 `ModelPicker` 选平台行 = 平台计费，选 BYOK 行 = 自担费用。多服务商列表在「设置·模型配置」（`user_llm_providers`：label + 密文 key + base_url + 内部连接测试种子）；日常选用在模型组合。行业对齐见 [`平台LLM接入.md` §二](/docs/05-平台与运维/平台LLM接入.md)。

**一道闸门**：所有用户向 LLM 调用（云回合 / file assist / sidecar 推理代理）共用 `billing/gate.py::preflight_llm_credentials(model_origin=…)`：

- `origin=byok`：解密本回合 `provider_id` 凭据（fail-safe；pinned 服务商不可用 → 回落账号默认）→ 有凭据直接返回（**不查配额**）；无任何服务商 → **402 `LLM_KEY_REQUIRED`**。
- `origin=platform`：平台凭据缺失 / byok 部署未开放代付 → 503 / 402；否则过 §一 `enforce_quota` 后用平台 key。

**计费语义（call 级凭据来源）**：`calculate_cost` 按**本次 call 实际凭据来源**算价，不读全局 `billing_mode`（`llm/pricing.py::resolve_credential_source`）：

- **用户 BYOK key** → **记账恒 0**（`cost_total_nano=0`），token 照记；另出**估算**落 `cost_estimated_nano`（永不进配额 SUM / 平台记账）。
- **平台主 key** / **厂商 extras key**（`doubao/` 等）→ 真实算价入账（整数 **nano-CNY**）。

**BYOK 估算**：两层价卡 `resolve_price_card`——社区快照 `estimated` → `unpriced`（不出数，**绝不回落默认价**）。社区快照抄的是各厂商官网 **USD** 标价，故估算金额币种为 USD、由 `estimated_currency` 标注（**仍无 FX**：不折人民币，见 §六·①）。`Cost.pricing_source` 贯穿台账 / SSE / REST；前端「≈$ + 估算」。platform/vendor：curated → 社区 → glm-5.2 回落 + `cost.pricing_fallback` warning。

**后台**（title / memory / compaction）：**平台凭据优先** + 一律 `enforce_quota`；平台不可用（配置缺失或上游 auth 拒绝）经 `run_background_llm` **一次**回落用户 BYOK。耗尽 → `None`（铸题降级 / 记忆跳过），不 429 主回合。→ [`平台LLM接入.md` §二](/docs/05-平台与运维/平台LLM接入.md)。原 followups（「下一步」chips）已下线。

**服务商管理面**：`/users/me/llm-providers`（列表 / 增删改 / test / defaults）。AES-256-GCM 落库，见 [`安全权限与治理.md` §七](/docs/05-平台与运维/安全权限与治理.md)。

→ 见代码 `billing/gate.py`、`billing/preference.py`、`llm/resolve.py`、`llm/provider_service.py`、`llm/pricing.py`、`api/routes/llm_providers.py`

> **已废**：独立「每月免费额度」路径（`free_tier_*` / `PLATFORM_FREE_TIER_ENABLED` / `FREE_TIER_EXHAUSTED`）。平台代付只走统一 `quota_*`。

## 一、三层防线

三层正交：限流挡「刷得太快」，配额挡「用得太多」，计费只忠实记录、不拦截。

| 层 | 位置 | 管什么 | 失败行为 | 现状 |
|---|---|---|---|---|
| **限流** | 路由层（按用户）+ 中间件（按 IP） | **速率**——单位时间内的请求次数 | 超额拒绝（429 + `Retry-After`） | ✅ 已落地（默认内存单进程；`RATE_LIMIT_BACKEND=redis` 切多 worker 安全的 Redis ZSET 滑窗，含请求级 fail-open） |
| **配额** | 业务层（回合开始前 **+ 每次上游 LLM 调用前**） | **总量**——日 token / 月成本 / **日成本** / 日请求数 | 开跑前超额 → 拒绝该回合（429）；回合中途超额 → 拒绝后续调用 | ✅ 强制已落地（含每用户覆盖 + admin `is_unlimited`） |
| **计费** | Finalize（append-only） | **记账**——每个 Run 的真实成本 | 失败 warning + 入共享 DB outbox 后台重试，不中断回合 | ✅ 已落地（详见 §三、§四） |

### 限流（速率防线，✅ 已落地）

两个互补的限流器（默认内存、单进程；配 `RATE_LIMIT_BACKEND=redis` 即切 Redis ZSET 滑窗，多 worker 安全）：

- **按用户限流**（✅ 路由层滑窗）：在消息发送 / 重新生成端点按已认证用户限频，挡单账号刷回合。因按用户需已认证主体，落在**路由层**（紧邻 `enforce_quota`）而非中间件；用**滑窗**（非固定窗口）避免边界 2x 突发；被拦的请求不记账。超额抛 `RateLimitedError` → 429 `RATE_LIMITED` + `Retry-After`。→ 见代码 `conversation/rate_limit.py`、`middleware/rate_limit.py`
- **按 IP 限认证端点**（✅ 中间件固定窗口）：限登录/注册/刷新端点（默认 10 次/60s），挡撞库；非 auth 路径与未登录请求放行。→ 见代码 `middleware/rate_limit.py::AuthRateLimitMiddleware`

回合开始前三道闸顺序：**限流（按用户）→ 所有权 → 配额**——限流最外，未过则不做资源级 DB 查询。

前端如何呈现「被拒回合」见 [`../04-前端/前端成本呈现.md` §7.6](/docs/04-前端/前端成本呈现.md)。

✅ 多 worker 限流：`RATE_LIMIT_BACKEND=redis` 经 `RateLimiter` protocol 缝切到 Redis ZSET 滑窗（`RedisSlidingWindowRateLimiter`）/ auth 固定窗（`RedisFixedWindowRateLimiter`），调用点零改动。✅ **请求级 fail-open**：Redis 请求期报错→放行（fail-open）并记 `rate_limit.redis_fail_open`（warning + 进程内累计 `count`，可告警）；只放松「速率」防线，DB 支撑的「总量」配额防线不经 Redis、不受影响；工厂构造期不可达仍回落内存。→ 见代码 `middleware/redis_rate_limit.py`

> **中期护栏（G5）**：账本队列已迁共享 Postgres ``cost_ledger_outbox``（每进程可自 drain，`FOR UPDATE SKIP LOCKED`）。生产多 worker **仅当** `RATE_LIMIT_BACKEND=redis` 时允许；`memory` 限流 + 多 worker 仍拒启（DEBUG 仅强警告）。**诚实边界**：审批门 / IM / steer / journal settlement 等仍可能是单进程姿态——**勿宣称全面多机就绪**。→ [部署拓扑 · API 进程约束](/docs/05-平台与运维/部署拓扑与环境.md#api-进程约束g5-中期)

### 配额（总量防线，✅ 强制已落地）

> 此防线管**平台代付路径**：`billing_mode=platform` 全员代付。**BYOK 有 key 用户不查配额**（用户自担上游账单）——这是**既定姿态而非缺口**（拍板 2026-07-20）：配额的产品目的是保护平台出资；BYOK 记账恒 0（估算走展示列，§〇·五）使金额口径配额天然不覆盖它属**设计使然**，勿当 bug 修。

| 决策 | 内容 |
|---|---|
| 检查时机 | **两道**：① 回合开始前（路由 `preflight_llm_credentials` → `enforce_quota`），超额 → 429 `QUOTA_EXCEEDED`，SSE 未开先拒；② **每次上游 LLM 调用前**（叶子围栏 `ObservingLLMProvider`），超额 → `LLMQuotaExceededError`（同 code、走叶子错误面，`retryable=False`），可中途拒。云内联与 sidecar 推理代理**同粒度** |
| 四维度 | 日 token / 月成本（CNY）/ **日成本（CNY）** / 日请求数；**0 = 该维度不限**。单一默认组 `quota_*`（`config/quota.py`）= **日 token 0 · 月成本 ¥5 · 日成本 ¥5 · 日请求 500**。**为何用日成本兜底**：多模型目录单价差 ~30×，日 token 帽映射不了钱 |
| 每用户覆盖 | `users` 表 `is_unlimited` + 四维度覆盖（NULL=继承全局；含 `quota_daily_cost_cny`）；`scripts/set_quota.py` 或 admin API（`PATCH /v1/admin/users/{id}`）设置 |

**为何逐调用（审计 D7 拍板 2026-08-13）**：只在回合开始查一次时，配额挡不住两种超卖——**并发回合**（同时开跑的回合各自读到同一个旧数字、全部放行）与**团队扇出**（一个 Multi-Agent 回合内部扇出多少 worker、跑多少轮完全不再复查）。sidecar 那条路本就逐调用查（每次调用都是一次 `/inference/` 请求，路由闸照跑），云内联路径不查 = 同一个产品承诺两条路一严一松。且 §六 已拍板**不做成本预估**，配额因此是跑飞风险的**唯一刹车**，必须真的拦得住。

**口径**：闸只管**平台代付**——判据是 call 级 `credential_source != user`（platform / vendor 都由部署出钱，`cost_total_nano` 非零），与计价侧同一判据，不另起启发式；BYOK 不查（上方既定姿态）。代理转发的调用不重复查（`/inference/` 路由已为同一次物理调用查过）。额度读走 **telemetry 池**（台账本就写在那），故逐调用读不与正文写抢 primary 池。

**诚实边界**：闸读 `cost_events`，而台账由 drain **持续**物化（in-process metering 每 call 即 enqueue + `materialize_runs=True`，drain loop 常驻），所以它看到的是「约一个 drain 周期前已落完的调用」——**在飞的调用不计入**。逐调用把超卖窗口从「整个回合」收到「一个 drain 周期」，**不是预扣额度**；要零超卖需同步计数器/预留，本案**有意不做**（会新增一层对账）。

→ 见代码 `conversation/quota.py`（`QuotaLimits.for_user`）、`billing/gate.py`（回合开始闸）、`billing/call_quota.py` + `llm/call_fence.py`（逐调用闸）

### 计费记账（✅ 已落地）

每个 **LLM call** 落一行 `cost_calls`（权威明细）；每个 **Run** 在 `cost_events` 有一行物化聚合（产品面工资单 / 仪表盘 / 配额 SUM 读这里）。云回合 finalize 双写聚合；sidecar 经云代理按 call 记明细并物化聚合。详见 §三/§四。

## 二、用量/成本不变量

token 与成本在系统中有多种形态（SSE wire、持久化、API 响应、计费台账），下列不变量保证不会算出两套数、也不会跨用户串账：

1. **唯一原始来源**：单次 LLM 调用的原始 `TokenUsage` **5 字段**（`input / output / reasoning / cache_hit / cache_miss`；`total` 为派生属性），所有用量从它累加。→ 见代码 `llm/provider/protocol.py::TokenUsage`
2. **唯一定价转换**：全系统唯一的 `calculate_cost(model, usage)` 把 token 折成钱（`input / cached / output` 三价分离，缓存命中按更低价计），任何地方要**记账 / 配额 / 用户面**成本一律调它，绝不另算单价。钱一律**整数 nano**（1 单位货币 = 10⁹），杜绝浮点；**记账侧恒 CNY**（`currency`），**估算侧随价卡原币**（社区表 = USD，`estimated_currency`），两侧都**无 FX**、绝不互折。**按 call 级凭据来源定价**（`resolve_credential_source`，不读部署级 `billing_mode`）+ **两层价卡**（`resolve_price_card`）：来源 `user` → 社区估算表 → unpriced（记账恒 0，估算走 `cost_estimated_nano` 展示列，见 §〇·五）；`platform` / `vendor`（厂商 extras）→ curated 价目表 → 社区表 → glm-5.2 回落。`Cost.pricing_source`（curated / estimated / unpriced）随钱贯穿到台账与 wire。展示元 = `nano_to_yuan`（nano/1e9）。→ 见代码 `llm/pricing.py`
   - **例外（运维只读，不进账）**：Admin Go 窗口另有一份 OpenCode **公开单价**读时估算（`billing/opencode_go_public_prices.py`，与 curated / 社区表分开放）。只统计池成员且端点精确匹配 Go（`/zen/go/v1`，禁止前缀）的调用；美元估算仅对价目表模型 `deepseek-v4-flash` 生效。只服务「离 $12 / $30 / $60 还有多远」，不写回 `cost_*`、不进配额、不进用户面。按每次调用时间戳判 Peak / Off-Peak，禁止均价。
   - **记账与估算永分离**：`enforce_quota` 月成本、admin 全站统计只 SUM `cost_total_nano`；`cost_estimated_nano` 是纯展示列（BYOK 工资单/仪表盘），两列互斥非零（`_split_cost`，`runtime/costing.py`）。**回合聚合同构双桶**（`aggregate_cost`，镜像 `db.repositories.billing._aggregate` 的 SQL rollup）：`input/cached/output/total` + `currency` 只收已记账行，故 `input + output == total` 恒成立；`estimated_total` + `estimated_currency` 只收 BYOK 行。取哪个数就必须读哪个币种字段——两桶绝不相加（混源回合是两种货币）。per-agent 分项仍在 `GET /messages/{id}/cost` 全量可取。
   - **缓存拆分对账**：输入费按 `cache_hit/cache_miss` 拆价。解析层（`TokenUsage.from_openai_wire`，网关 / 推理代理 / 视觉读图共用）兼容两种线上方言：DeepSeek 显式拆分（`prompt_cache_{hit,miss}_tokens`，优先）与 OpenAI 风格 `prompt_tokens_details.cached_tokens`（hit=cached、miss=prompt−cached 推导）——否则 OpenAI 方言上游的缓存命中恒报 0，平台价卡（如 gpt-4o）把命中全额按 miss 计价、账单虚高。两种方言都缺时，计价层仍按 `cache_miss = max(input_tokens − cache_hit, cache_miss)` 对账——原生路径（`hit+miss==prompt`）恒等无副作用，缺拆分时整段 prompt 按 miss 计，保证「被计价的输入 == prompt」永不落空。用户面 `UsageBreakdown` 投影（消息 REST / 用量 API）对省略形 `input>0 且 0/0` 用同一 guard 填 miss；解析层 0/0 原形不动（计费公平绊线）。展示文案只说「按未命中计价」，不断言上游命中为 0。
   - **命中率可观测**：拆分出的 `cache_hit/miss` 每次调用配一条 `cost.prefix_cache`——命中率 + 这次为何没能全量复用上次前缀（改了系统提示的哪一段 / 中途改写历史 / 纯追加）+ 按 prompt 规模分桶，`cache_reported=false` 表示上游根本没报缓存字段（**不等于 0% 命中**，不进任何比率）。默认 info 不落 jsonl（debug，给 `llm.call` 腾窗口）；查 D4 须 `LOG_LEVEL=DEBUG` → 见代码 `observability/prefix_cache.py`。
   - **回落可观测**：未知/未配置 `model` 回落 glm-5.2 价（缺价绝不腰斩回合），故回落时打 `cost.pricing_fallback`（warning）而非静默，便于从日志发现漏价。

**真正的钱以 `cost_events` 台账为准**（不变量 #1）；`Message.usage` / `runs` 里的成本只是展示快照。新增任何成本展示点 → 复用统一定价函数，勿手算单价。

3. **会话归属不在写路径校验**：`cost_events.conversation_id` **无**指向 `conversations` 的 FK；推理代理写入不查「该会话是否属当前用户」。会话口径读侧一律按 `(user_id, conversation_id)` 收敛，账户口径按 `user_id` 收敛（账户级行无会话，见 §三），两者的 `user_id` 都来自鉴权令牌 → **无跨用户泄漏**；伪造/错挂 id 至多把本人花销记到本人账本里无权的会话上。热路径不加归属 DB 查是有意取舍。→ 见代码 `api/routes/inference/proxy.py`（写头注释）、`db/models/billing.py`

## 三、台账：per-call 明细 + per-run 聚合（✅ 已落地）

| 决策 | 内容 |
|---|---|
| 粒度（②） | **per-call 明细（`cost_calls`，权威）+ per-run 物化聚合（`cost_events`）**。云回合与 sidecar（经云推理代理）同构：代理侧按 call 记明细并按 `run_id` 物化聚合；云 in-process 经 `log_llm_call` → call meter 入明细并 **同步物化**（`materialize_runs=True`），turn finalize 再按 `message_id` 从 `cost_calls` 对账 upsert（补齐 pause/resume / 协调波次下内存 `cost_runs` 漏折的 worker），vision 等仅在 `cost_runs` 的孤儿行再 `record_runs`。明细携带 `role`（结构桶）+ `persona`（人设标签，如「调研员」）+ `run_id`/`agent_id`/`parent_run_id`。平台代付另有 `platform_credential_id`（池成员 = 该行 UUID；env / 覆盖 = `PLATFORM_CREDENTIAL_ID` / JSON `id` 或 `(api_key, base_url)` 哈希，非 key 明文；BYOK 为空）。只进日志与台账，**不进**用户可见 SSE error context |
| 货币（①） | 整数 nano-CNY（`currency=CNY`）；冗余 `cost_total_nano`（记账）与 `cost_estimated_nano`（BYOK 估算，展示专用）双标量列供窗口 SUM，两列互斥非零 |
| 幂等 | 明细 `call_id` unique；聚合 `run_id` unique（finalize DO NOTHING；代理物化 DO UPDATE） |
| 写入时机 | 每成功 LLM call → 明细；turn finalize / handoff / **incomplete 收口**（`/stop` · sweeper · process_kill → `close_turn_interrupted`）/ 代理物化 → 聚合；与 assistant message 共享 `message_id`（背景调用 NULL；账户级 chrome 连 `conversation_id` 也 NULL，见下）。interrupt 路径 `cost_runs=[]` 只物化已有 call，不伪造 orphan；成功后 emit `cost.recorded`（含 `by_role`）并盖 `messages.cost`（已盖则跳过 emit，防双记日志） |
| 写入失败语义 | 同步写失败：warning + **入共享 DB outbox 后台 drain 重试**（at-least-once）；回合正文已先提交，不因账本失败回滚 |
| 失败 run 计费 | 硬失败（worker `raise_on_error` 抛错、CEO/续跑循环崩溃）仍按**已完成轮**入账——`usage_sink` 把已计量 usage 从抛点带出，经 `calculate_cost` 折钱落 `FAILED` 行（token 已真花在用户 key 上，漏记 = 平台/用户白付）；用户主动取消（`CancelledError`）**不为取消本身造 FAILED 折算行**（`except Exception` 不捕 `BaseException`）——但**已成功 call 仍在 incomplete 收口时对账**（见上「写入时机」）。vision 等仅挂内存 `cost_runs` 的孤儿在 cancel 时可能仍漏物化（本案不抢救） |
| 真相源 | `cost_calls`（明细权威）；`cost_events` 为产品读侧聚合视图；`Message.usage` 仅展示快照。开发期无历史回填——老行可缺明细/`persona`；单回合工资单与 `cost.recorded` 读侧可用 `COALESCE(persona, role)` |

**账户级行 · 不属于任何会话（✅ 已落账）**：**AI 改写**（文件工作台划词改写）与**文档 description 自动补**真花 token，却压根不属于任何会话。台账三张表（`cost_calls` / `cost_events` / outbox）的 `conversation_id` 原本 NOT NULL，call meter 只能整条丢弃——拍板**放宽账本**（钱花了就该看得见）：三处列改**可空**，role CHECK 加 `assist` 桶，`persona` 记是哪条 chrome（「AI 改写」/「文档摘要」）。这类行只挂 `user_id`（`conversation_id` / `message_id` 均 NULL）；**绝不编造会话 id** 把花销挂到用户某条无关对话上（该特例层已否决）。唯一硬要求是有付费账号：无 `user_id`（eval / 设置·测连探针）仍不记。

读侧两类口径都是**结构性**的，不是特例分支：**账户窗口全收**——`aggregate_for_window`（用量页今日/本月 + 仪表盘趋势 + `enforce_quota` SUM）、`aggregate_by_model_for_window`（各模型）、`aggregate_by_user_for_window`（全站工资单）都只按 `user_id` + 时间窗聚合；**会话 / 回合口径天然不收**——对话累计按 `conversation_id` 等值、单回合工资单与复盘按 `message_id`，NULL 一律匹配不上（admin 对话名册的 per-conversation SUM 另显式 `IS NOT NULL`，免得空分组空转）。故这笔钱与 token 照进额度，**「请求数」不被抬高**（`COUNT(DISTINCT message_id)` 忽略 NULL，与 标题/记忆 背景调用同口径）。逐调用配额闸一如既往只读 `user_id`，额度耗尽照样拦得住。→ 迁移 `d5b8c2f7a1e4`

→ 见代码 `billing/ledger_call.py`（in-process / proxy 共享 `CallCost` 装配）、`runtime/costing.py`、`db/repositories/billing.py::CostEventRepository`、`billing/attribution.py`、失败计费 `runtime/runs/executor/shared.py::_priced_failure`

## 六、成本预估：❌ 有意不做（2026-08-13 定案）

**本节此前把「团队组建时给启发式预估」记为已实现**（含固定假设：Captain 跑 3 轮、队员各 2 轮、每轮约 3000 输入 + 700 输出 token），**代码里前后端均不存在**——属文档超前于实现，已按审计议题 D1 拍板改为否决。

**否决理由**：单个多 Agent 回合的真实消耗取决于任务复杂度、模型自主轮数、工具调用次数与实际派工数，事前方差极大（同一张卡可能是三毛也可能是十五块）。给出的数字会被用户当成保障——**误导性预估比没有预估更糟**。

因此授权开工卡**有意不带金额**，运行中状态条同样不带；用户看到的第一个数字仍在回合结束后（`cost.recorded` / 气泡 meta）。

**跑飞风险的兜底就是配额本身**：platform 代付路径由 §一 配额防线拦——正因为它是唯一刹车，D7 已把该检查下沉到**每次上游调用**（并发回合 / 团队扇出都拦得住，见 §一）。BYOK 用户不查配额（自担上游账单，§一既定姿态），故平台侧无刹车——这是 BYOK 姿态的自然结果。**同时否决**「运行中累计金额」这条替代路：它与 §「三级呈现」的「对话累计 caption 已退役（零噪音）」互斥，要做须先推翻那条定案。
