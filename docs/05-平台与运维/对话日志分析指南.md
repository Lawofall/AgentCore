# 对话日志分析指南

> **Why**：产品 AI 回合的结构化事件在 `logs/dev.jsonl`（JSONL），完整正文在 Postgres——查失败回合靠 **trace_id 全链路**，不是搜 Cursor 转录。日志只支撑个案与存在性，不支撑产品取舍或占比外推；何时打开 → [`.cursor/rules/conversation-logs.mdc`](/.cursor/rules/conversation-logs.mdc)；按问题选证据 → [`.cursor/rules/dev-process.mdc`](/.cursor/rules/dev-process.mdc)。
>
> **How（操作步骤权威）**：仅当用户给出 32-hex / UUID / 排查包，或明说查失败 / 巡检时 → **只读** [`.cursor/rules/conversation-logs.mdc`](/.cursor/rules/conversation-logs.mdc) CLI 开查。讨论产品或架构默认不打开。本文不重复 CLI；**单次贴 ID 勿整篇读本文**（词表 / Token 两口径 / 接缝深挖再开对应节）。
>
> **默认证据面**：`log_timeline` 人读与 `--json` = **`decision_spine`**；全量事件流用 `--raw`。现码 `spine_events` = **turn_spine**（会话 turn 目录），不是产品面。脊上 **Decisions** 仍是决策/失败点（含失败 `tool.execute_end`、`llm.call_failed`）；**Exec** 是折叠执行面（工具按名聚合、`obs.turn_spans` 只抽 `invoke_agent` 行、prepare 分段一行）。成功工具跨度与逐条 `llm.call` 不铺上脊。
>
> **排查包**：`--pack <dir> --trace <tid>` 写出可投递目录——必有 `decision_spine.json`（契约 v0）+ `timeline.jsonl` + `meta.json`（含 `schema_version` / `layers` / traffic / jsonl 断档 / 导出时间）；有 join 时附 `turn_metrics.json` / `messages.preview.json`；store 有 journal 时附 `journal.redacted.jsonl` + `journal.summary.json`（允许名单脱敏，**永不**带用户对话 / LLM body / 工具原文）。显式 `--full` 才带 `messages.json`（仍无 LLM body、仍无 raw journal）。另一会话只读包内文件即可复盘。失败回合（`turn_end` 为 `error` / `degraded` / `unproductive`）在 `persist_turn_journal` 成功后立刻 best-effort 写 journal-only 包到 `logs/packs/<trace_id>/`（仅 `meta.json` + `journal.redacted.jsonl`，同一脱敏白名单；**不等** jsonl、不走 `query_trace`）。`cancelled` / `paused` / `end_turn` 不打。`--trace` 查编号时若这份自动存档还在，人读多一行 **Auto pack**，`--json` 见 `meta.failure_pack`。满 30 天删除时记 `journal.failure_pack_gc_expired`（删了哪份）。完整 `--pack` 仍要 CLI。
>
> **Dogfood 入槽**：出包后仓库根 `python evals/dogfood/fill_from_pack.py --pack <dir>` 写入空 `pending_label`（只填真实 id；三维分可选人工）。最短路径 → [`evals/dogfood/README.md`](/evals/dogfood/README.md)。

## 症状进层

先按症状进层，再开对应证据。排查包 `meta.layers` 标明包内有哪几层（`decision` / `execution` 恒有；`turn_metrics` 随文件；`sidecar_host` 恒 `not_in_pack`）。journal 有无仍看 `meta.journal.mode`，不设 `layers.journal`。

| 症状 | 进哪层 | 禁止 |
|---|---|---|
| 流停了 / 工具失败 / LLM 挂 / 审批超时 | `--pack` 或 spine **Decisions**；执行折叠看 **Exec** | 先改前端 fold；默认 `--raw` |
| 刷新后假生成中、假 pending、卡复活 | 前端 hydrate / `coldSettlement`；journal 是否已有 `*_resolved` | 只 `sync:logs` 对着空云端猜 |
| 横幅 `turn already running` | 安装机 `userData/logs/desktop.jsonl`（`sidecar.turn_already_running`）；冷 resume 撞槽看 `resume.deferred` | `pnpm sync:logs`（本事件不进云端） |
| `ResumeJournalDegradedError` / 无法恢复挂起 | journal 是否缺 `turn_started` | 空窗续跑；用 frame transcript 猜 |
| 本机 `turn_metrics` token 为 0 | 已知口径（本机行 token 空）；看 `llm.call` / `cost_events`，按 `mode=cloud` 滤 token 面 | 当「没花 token」修账 |
| 协议 / 呈现与后端向量不一致 | `pnpm conformance`、`#/preview` | 先加 jsonl 埋点 |
| 「本机暂时跑不了命令：最短一句 5 秒都没跑完」 | `exec_env_probe_timeout`（`sandbox.exec_env_probe_failed` / `coordination.exec_env_dead_user_notice`）。host `content_delta`，落库正文常没有。jsonl 遇 `cost.ledger_drain_failed` 洪水会把开场事件轮转掉 → `--export-dir` + 同会话后半夜 `chat.local_turn_tool_failures` | 只在空 `dev.jsonl` 里找正文 |
| 气泡说 AgentCore 挂了，脊上却是厂商 5xx / 530 | `llm.upstream_error` / `llm.inference_envelope_relay`；信封是否被 `body_preview` 截断 | 把对面故障改成「我们挂了」 |
| 刚重启后端，但 `ceo_prompt` / `assembly_hash` 仍与改前相同 | `chat.turn_start.via`；对账 `sidecar.ready` vs `server.started`。本机传统引擎在 sidecar → [本地开发 · 改代码后哪边会加载](/docs/02-架构/本地开发.md#改代码后哪边会加载) | 把「没委派 / 仍像旧核」判给刚改的 prompt |

桌面支持包脱敏（安装机侧）→ `apps/desktop/src/shared/desktop-log-sanitize.ts`；**不**把 `desktop.jsonl` 打进云端 `--pack`。

### 已有 trace 后扫脊

默认脊覆盖决策收口 + **折叠执行面**。进 **Decisions / Exec** 层之后：

1. `uv run python scripts/log_timeline.py --trace <trace_id>`（线上先 `pnpm sync:logs` 再加 `--export-dir ../../logs/prod-export`）。
2. 扫 **Decisions** 里的失败点（`tool.execute_end` / `llm.call_failed` / `run.failed` / `pipeline.error` / 审批超时 / sidecar 取消）。
3. 看 **Exec**：工具按名 `ok/err`（成功调用不逐条铺）；`obs.turn_spans` 只抽 `invoke_agent` 行（失败优先）；**Prep** 是 `chat.prepare_phase` 一行。
4. 看 **LLM** 合计 + `scenario` + `slowest`（≥2 次调用时）；失败那次在 Decisions。若有降级，人读脊多一行 **Degraded**（`decision_spine.degradation`，仅计数 >0 时出现）→ [运行时总览 · 韧性地图](/docs/03-AI核心/运行时总览.md#韧性地图)。若回放没写上，人读脊多一行 **Replay  这一轮的回放没存上**（`decision_spine.replay_persist`，有 `journal.persist_failed` 才出现；回答当时仍会给用户）。
5. jsonl 断档或需要 SSE 事实序 → `--pack` 读 `journal.summary.json`（kind 计数 / 失败 run·工具）和 `journal.redacted.jsonl`（无用户对话）。

仍要 `--raw` 的：逐条成功 `tool.execute_end`、逐条成功 `llm.call`、`LOG_LLM_BODIES` 的 request/response、以及本机 `sync:logs --full` 才有的 **raw** journal（排查包永远不带）。

## 接缝（日志 ↔ DB）

| | 产品 AI 日志 | Cursor IDE 会话 |
|---|---|---|
| 位置 | `logs/dev.jsonl`（仓库根；20MB 轮转） | `agent-transcripts/`（与产品无关） |
| ID | `trace_id` = **32-hex 无连字符**；`conversation_id` = UUID | 文件名 = 带连字符 UUID |

- **全链路键**：`trace_id`（同一次用户交互，含进程内委派）；会话 → `conversation_id`；单次回合运行 → `attempt_id`；持久回合 → `message_id`（≡ journal `turn_id`）。
- **请求级客户端**：`client_platform` / `client_version` 由 `RequestAttributionMiddleware` 绑进 contextvars（与 `http_method` 同级，低基数，不是每事件手传）。缺头 = `-`，传了空串 = `""`；非 HTTP 任务没有这两个键。按版本看症状是否只在未升级客户端：`jq -r 'select(.conversation_id) | [.client_platform // "(no-http)", .client_version // "(no-http)", .user_id, .conversation_id] | @tsv' logs/prod-export/*.jsonl | sort | uniq -c | sort -nr`。
- **`chat.turn_start.via`**：执行路径 `sidecar|cloud`，与工作区 `location`（local/server）正交；decision_spine head 会抽取。引擎在哪跑是第三轴（`turn_metrics.mode`，与 `finalize(mode=)` 同源）→ 下「本机回合与 turn_metrics」。
- **本地回合 spine**：sidecar 回写后云端认 `chat.local_turn_recorded` 为 decision_spine head+close 锚（**禁止**再冒充双写 `chat.turn_start/complete`）；工具失败粗码/工具名见 `chat.local_turn_tool_failures` → spine `decisions`（不发假 `tool.execute_end`）。
- **本机互斥拒**（横幅 `turn already running`）：进层 → [症状进层](#症状进层)。
- **DB join**：`messages` / `cost_events` / `run_sessions` 带 `trace_id`（assistant / 落账有值；user / handoff 常为 `NULL`）。`turn_metrics` 现含云端与本机 sidecar 回写（本机 token 仍空，见下「本机回合与 turn_metrics」）。键集合权威 → [后端架构 · Context 注入](/docs/02-架构/后端架构.md)。
- **不落完整正文**；`preview` / `reply_preview` ~200 字；`LOG_LLM_BODIES` 开时有截断脱敏 `llm.request`/`response`。
- **模块入口**：事件注册表 `observability/catalog.py`（`sync_log_event_registry.py` 生成）；查询层 `observability/query/`；CLI `log_timeline.py` / `log_stats.py`。新增埋点写 `logger.info("component.action", …)` 后 sync——**勿手改**下方事件表。

## 委派验收事件

引擎不按验收 kind 硬判。统一说法：

| 事件 / 字段 | 现行？ | 语义 |
|---|---|---|
| `delegate.acceptance_resolved` | ✅ 现行 | 工人开跑时仍打；`criteria`/`source` 现为 `null`（无 kind binding） |
| `delegate.completion_criteria_ignored` | ✅ 现行（观测） | CEO 误传已删字段时打点；忽略字段，非硬闸 |
| soft overlays | ✅ 现行 | TS 落盘验证提醒、import 图闭合自动扫等仍为 soft note：不挡批次，经 `delivery_status`（`severity=warning` → `state=notes`） |
| deliverable / contract 缺口 | ✅ 现行 | 仍走 `delivery_status` + CEO 复盘；错收工接盘靠提示词 + soft + 人审 |
| `delegate.completion_criteria_unmet` / `…_hoisted` | ❌ 历史兼容 | **不再**由引擎按 kind 触发；catalog / spine 仅读旧 JSONL；勿当现行契约 |

历史日志里可能仍见 `completion_criteria_unmet` / 非空 `criteria`——那是 S3 前回合。

## Token 两口径（decision_spine vs turn_metrics）

复盘时 **`llm.*_tokens` ≠ `tail` / `turn_metrics` tokens 不一定是 bug**：

| 口径 | 来源 | 含义 |
|---|---|---|
| **llm**（spine） | 同 `trace_id` 全部 `llm.call` 合计 | **全 trace**（含 pause 前） |
| **tail / turn_metrics** | 收口折账（`turn_metrics` 优先，否则 JSONL close） | **本段结算**；`kind=resume` / `chat.resume_complete` 通常只有 resume 段 usage |

spine JSON：`llm.token_scope=full_trace`；`tail.token_scope=settlement` 或 `settlement_segment`（resume）；`health.token_accounting` 有短说明。人读 timeline 在两数不一致时会打 `Token口径:` 行。**勿把差值当计费漂移去改账**——先看是否 resume。窗口合计怎么滤本机行 → 下节。

## 本机回合与 turn_metrics

sidecar 回写（`_finalize_local`：完成 / 暂停 / 取消）也会 best-effort 落一行 `turn_metrics`，与云端同一张表。本机回合 join 认这行；没有时 Tail 才退回 `jsonl_close`。

只写**结构字段**：`status` / `finish_reason` / `rounds` / `duration_ms` / `kind` / `delegated` / `workers`。`delegated` / `workers` 与同回合 `team_batch` 同源（`kind != no_batch` / `worker_count`），不另造人数口径。

**`mode` 标引擎在哪跑**，与 `finalize(mode=cloud|local)` 同源。不等于 `chat.turn_start.location`（工作区在用户盘还是服务端），也不等于 `via`（`cloud` / `sidecar`）——三者正交。旧行回填 `cloud` 是事实（当时只有云端写行），不是 unknown。

**token 字段仍空**（本机推理经云代理，折账只在 cloud finalize；未对齐）。本机行的 `input_tokens` / `output_tokens` 为 0 **不是**「没花 token」——看 `llm.call` / `cost_events`。**token 面按 `mode = 'cloud'` 过滤，不要按 `input_tokens = 0` 排除**——云端真实零 token 失败回合会被一起误伤。

**覆盖面变化**：补行后 metrics 含本机回合。跨窗对比（补行前 vs 后）的回合数 / 委派率 / 错误率会跳，勿把 diff 读成产品质量突变。落点 → [管理员后台](/docs/05-平台与运维/管理员后台.md)。
