# 部署拓扑与环境

> **权威范围**：自托管服务器环境、网络域名、Compose 编排、容量取舍、配置分层与种子数据。
> **入口**：[部署与运维](/docs/05-平台与运维/部署与运维.md) · **发版/门禁** → [发布与门禁](/docs/05-平台与运维/发布与门禁.md)
## 一、服务器环境

### 域名拓扑（参考自托管）

公开文档用占位域名描述角色；自托管时换成自己的 DNS。品牌官网可另配。

| 角色 | 示例主机名 | 典型路由 | 用途 |
|------|-----------|---------|------|
| API + web 客户端 | `app.example.com` | A/AAAA → 应用机 Nginx | API（`/api`）+ `dist-web` 同源 SPA |
| 手机网页 | `m.example.com` | **已下线** | 旧独立 SPA / Pages 已删；窄屏走 `app.` 同源 `dist-web`。**Capacitor 安卓壳**仍须 `https://localhost` 等（见 §7.6a） |
| 官网 | `www.example.com` | Pages / 静态托管 | `apps/website` |
| 品牌下载 | `downloads.example.com` | 自有机 nginx + Tunnel（可换国内 OSS） | 版本检查 feed / `latest.json`；**官网与桌面安装包**走 GitHub Releases（§7.6b） |
| 管理后台 | `office.example.com` | 反代或 Tunnel → 本机回环端口 | `apps/admin` SPA；建议再加身份门（如 Access） |
| 可选中转 | `relay.example.com` | Tunnel / 反代 | 仅在启用对应能力时需要 |

生产具体主机名、Tunnel ingress 与机上 Nginx 全量配置**不入仓**；仓库只提供 `deploy/nginx/*.conf` 片段与 compose 蓝图。

> 硬件规格、公网 IP、SSH 密钥路径等运维快照**不入 docs**（随实例漂移）；需要时查运维 runbook 或云控制台。

### 预装软件（决策）

Docker + Nginx + certbot（自动续签）+ ufw（22/80/443）+ fail2ban。Docker 端口绑定 `127.0.0.1`，不对外暴露。

## 二、网络与域名

### Cloudflare Tunnel

Tunnel 可承载管理后台 / 可选中转 / 通配符兜底；apex 官网亦可改走 Cloudflare Pages 等静态托管。配置细节不入 docs（运维 runbook）。

### Nginx 反代决策

| 决策 | 内容 |
|---|---|
| `/api/` | 反代后端 API，**关闭缓冲**以支持 SSE 流式 |
| `/storage/` | 反代 MinIO，**Host 头改写**为 `minio:9000` 以匹配 SigV4 签名 |
| 安全头 | HSTS / nosniff / X-Frame-Options DENY |
| 上传上限 | `client_max_body_size 100m` |

具体 server 块由自托管机上的 Nginx 配置承载（运维注记，不入 docs）。

### 官网（Cloudflare Pages）

营销官网部署在 **Cloudflare Pages**（Next.js 静态导出），与后端解耦、零服务器占用。

| 项目 | 值 |
|------|------|
| 项目名 | `agentcore-website` |
| 源码 | `apps/website`（Next.js 静态导出，`output: "export"`） |
| 构建 | `next build --webpack`（**不可用默认 Turbopack**：Next 16 下 Turbopack 不产出 `out/`，会部署成空站） |
| 部署 | 本地脚本 + wrangler direct-upload（✅ `pnpm -C apps/website deploy:pages`） |
| 凭据 | 本地 deploy env（示例名 `deploy/.env.deploy.local`；**不入仓**） |

**部署决策**（2026-06）：不再用 GitHub Actions `push` / `workflow_run` 自动部署官网。

| 方案 | 结论 |
|---|---|
| Cloudflare Pages **Git OAuth 集成** | **否决**——现有项目是 direct-upload 类型，改接 Git 须重建项目并迁移 apex 域名 |
| GitHub Actions + wrangler | **否决作为唯一主路径**——Actions 分钟不足时不可靠；保留 `workflow_dispatch` 备用 |
| 本地 build + wrangler | **采用**——与 direct-upload 模型一致；凭据本地配置、不入仓 |

✅ 已落地（官网 + admin）：`pnpm -C apps/website deploy:pages` / `pnpm -C apps/admin deploy:production`；GHA 对应 workflow 仅 `workflow_dispatch`。根 `package.json` **无** `deploy:pages` 脚本。`apps/mobile deploy:pages` **已退役**（独立 `m.` 站已下线）。维护者用 Cursor 时的可选细则 → `.cursor/rules/cursor-deploy.mdc`（非自托管必做主路径）。

→ 见代码 `apps/website/package.json`、`apps/website/scripts/deploy.mjs`

### 手机网页版（已下线）

旧 `apps/mobile` Vite SPA（Bearer、Cloudflare Pages、`m.example.com`）**已删**。窄屏产品页就是 `app.` 上的同源 `dist-web`（cookie，零 CORS）。不要再把桌面树挂到 `m.` 当第二套鉴权。

| 项目 | 值 |
|------|------|
| 现状 | Pages 项目已删；主机不再提供产品面（不 301） |
| 自定义域 | 已从 Pages 摘除。本仓库 Pages token **不能改 Zone DNS**；残留 A/CNAME 须在 Cloudflare Zone 控制台手删 |
| 后端 | `CORS_ALLOW_ORIGINS` 已不含 `https://m.example.com`。**Capacitor 安卓壳**仍须含 `https://localhost`（及 `capacitor://localhost` / `http://localhost`），否则 App 会报「无法连接后端」 |

→ 见代码 `apps/mobile/scripts/deploy-pages.mjs`（调用即失败，防止误发 stub）

### web 客户端（同源 · 服务器 Nginx）

主力 web 客户端（`apps/desktop` 渲染层跑在浏览器，形态 A：web = 「云工作区」一等入口）**同源**部署在 **app. 根路径**：页面在 `https://app.example.com/`、API 在 `https://app.example.com/api/`，由**同一台 Nginx** 托管 → 第一方 cookie、**零 CORS**。选同源而非另开静态子域的理由：cookie 鉴权同源最稳，且 API 已在该 Nginx 上，加一段 `location /` 即可。

| 项目 | 值 |
|------|------|
| 源码 | `apps/desktop`（Vite 渲染层 webapp 入口 → `dist-web/`） |
| 构建 | `pnpm --filter agentcore-desktop build:webapp`（`.env.production` 指向你的 API 同源 URL） |
| 静态目录 | `/opt/agentcore/web/dist` |
| 部署 | 同步静态产物后 `nginx -t && reload`（**仅同步文件，不改 server 块**） |
| Nginx | 一次性把 `root` + `location /` + `/assets` 合入 app. `:443` 块；**勿动** `/api`、`/storage` 等——参考 `deploy/nginx/app-web.conf` |
| 后端 | 同源 → **无需 CORS** |

→ 见代码 `apps/desktop/scripts/deploy-web.mjs`、`apps/desktop/package.json`、`deploy/nginx/app-web.conf`

### 管理后台（独立 origin）

运营控制台（`apps/admin`，Cookie 鉴权）建议部署在**独立 origin**，由 Nginx（或等价）提供静态文件，外层再加身份门（可选）。参考片段：`deploy/nginx/office-admin.conf`。

| 项目 | 值 |
|------|------|
| 静态目录 | `$AGENTCORE_HOME/admin/dist`（默认 `/opt/agentcore/admin/dist`） |
| Nginx | `deploy/nginx/office-admin.conf` |
| 构建 | `VITE_API_URL=https://app.example.com/api`（换成你的 API） |
| 部署 | SSH / CI 将产物同步到静态目录后 reload 反代 |
| 后端 | `CORS_ALLOW_ORIGINS` 须含管理后台 origin；首次 `create_admin.py` |

凭据：SSH / 部署 token 写在本地 deploy env（**不入仓**），勿把私钥路径写进文档或提交。

→ 见代码 `apps/admin/package.json`、`apps/admin/scripts/deploy-production.mjs`、`deploy/scripts/admin-remote-install.sh`

## 三、容器编排

> **实现现状**：自托管默认布局为 `$AGENTCORE_HOME`（通用默认 `/opt/agentcore/`）。仓库 deploy 资产（dev/server/app compose、Dockerfile、`deploy-server.sh`、`production.env.example` 等）→ 见代码 `deploy/`。日常发布：本地脚本 `pnpm deploy:backend <sha>` 预构建、空闲后 `:switch` 切流；GHA `build-backend.yml` / `deploy-backend.yml` 仅 `workflow_dispatch` 备用。Nginx 片段见 `deploy/nginx/`。仍 ⏳：worker 容器。
>
> **自托管提示**：活栈目录通过 `AGENTCORE_DEPLOY_DIR` 指向（默认 `…/repo/deploy`）。机上私有快照目录属运维细节，不在此展开。

### 镜像仓库

容器镜像仓库（如云厂商 ACR/GHCR）的公网推送端点与内网拉取端点由 `ACR_*` / `IMAGE_REGISTRY` 配置；示例见 `deploy/config/production.env.example` 与 `build-backend.yml` 注释（占位 `registry.example.com/your-namespace`）。

### Docker Compose 文件

仓库内部署资产（dev/server/app 三 compose + `apps/server/Dockerfile` + `deploy-server.sh` + `production.env.example` + `searxng/settings.yml` + `init-db.sh`）→ 见代码 `deploy/`。仍 ⏳ 未纳入：

| 文件 | 用途 | 状态 |
|------|------|--------|
| worker 容器（api/worker 全量编排） | 独立 worker 入口；当前进程内协程，无 | ⏳ 暂缓 |

> SearXNG：**prod** 引擎集偏国内可达（`keep_only`: baidu / sogou / bing，见 `deploy/searxng/settings.yml`；360search / quark 已因云 IP 反爬静默 0 结果剔除）。**dev** 另用 `settings.dev.yml`（国际引擎为主 + baidu/sogou 辅）——勿把 prod 引擎集当成 dev 口径。应用经 `SEARXNG_URL`（默认 `http://localhost:18888`，与 `config/search.py` 一致；API 同 compose 网络时用 `http://searxng:8080`）连接；api **不** `depends_on` searxng（未就绪则 probe 降级）。**生产建议**配 `TAVILY_API_KEY` 作主搜失败备腿（空 = 无备腿）；见 `deploy/config/production.env.example`。SearXNG 侧 `GRANIAN_WORKERS=6` 与应用 `_SEARCH_CONCURRENCY=6` 对齐（改 workers 需 recreate searxng 容器）。镜像 digest 钉在 `docker-compose.server.yml` / `docker-compose.dev.yml`（勿盲跟 `:latest`）。

### 当前容器清单

目标态容器以 `deploy/docker-compose.server.yml` + `deploy/docker-compose.app.yml` 为真相源；默认再叠 `docker-compose.sandbox.yml` 起独立 **`sandboxd`**（不是第二份 API 进程）。可选遗留组件取舍见 §六。官网走 Cloudflare Pages（§二）。

### 云端执行（gVisor）

> 执行模型 / 护栏语义权威见 [安全权限与治理 · 五、代码执行沙箱](/docs/05-平台与运维/安全权限与治理.md)；本节只写部署面。
>
> **目标（第一刀 ✅）**：执行面是独立沙箱服务，不是 API 容器里的第二进程。开通在回合外；API 只 RPC。切流 **替换** 旧「sandboxd 叠进 api」拓扑，不留 in-API guest 回落。
>
> **目标（第二刀 ⏳）**：完成态与否决 → [安全权限与治理 · §五 代码执行沙箱](/docs/05-平台与运维/安全权限与治理.md)。部署：`PREVIEW_PUBLIC_BASE_URL` 为公开 preview origin（空 = mint 503）；sandboxd 预览 HTTP compose 发 `127.0.0.1:8787`（勿 `0.0.0.0`）；宿主 nginx 独立 origin 反代该口并 Upgrade WebSocket（`deploy/nginx/app-web.conf`，不是 app SPA）。API 不提供预览字节。Unix socket RPC 面不变。本机换票+反代狗粮（不需要 runsc）→ [本地开发 · 云端用户预览（第二刀）本地狗粮](/docs/02-架构/本地开发.md#云端用户预览第二刀本地狗粮)。
>
> **现状**：代码 `gvisor_enabled=true`；`deploy-server` / `finish-server` **默认叠** `docker-compose.sandbox.yml`（独立 `sandboxd` 服务）。部署 AI **不必**再勾选开关。紧急关闭：机上 `GVISOR_ENABLED=false` 后 finish。沙箱不健康 → 不拒启、执行类与云浏览器诚实不装配。验收看能力行：`code_execute=` / `package_install=` / `browser=` 同一谓词（云桌 guest 能起且当前盘已挂；`browser=已装配` 不是右坞已有帧）。
>
> **云端浏览器**：`location=server` / 新云桌 **只**走 gVisor Sandbox 浏览器（右坞 SSE 直播）；**禁止** DesktopBridge loopback 冒充云可达。开发机 **Windows 本机 API** 无法跑 runsc → 云工作区预期 `browser=未装配`（属环境，非产品缺口）。本地要验收云浏览器：API 须在带沙箱的 Linux（staging / Linux VM 容器）。真·本机右坞 → 绑本机文件夹走 Bridge，与云隔离浏览器不同路。

**部署步骤**（默认开；仅紧急关。启动期健康探测失败**不拒启**，打 `sandbox.cloud_health_failed` warning 并按能力诚实不装配——fail-safe，不存在悄悄回落 subprocess / DesktopBridge。**开齐口径**：云桌 guest 真 `runsc`（`--platform=systrap --network=sandbox --ignore-cgroups` + netns + 当前工作区 rw-bind）→ `code_execute=` / `package_install=` / `browser=`（Chromium 在同一 guest 内）。禁止用 `ip netns add` 冒烟代表 guest 能起。失败日志 `reason` 含 `not_linux` / `runsc_failed` / `sandboxd_unavailable` / `NetnsError` / `os_error` 等）：

1. **镜像**：`apps/server/Dockerfile` 已内置 runsc 下载层（官方源 `storage.googleapis.com`；官方源拉不动时 `--build-arg RUNSC_URL=<镜像源>`，无校验文件的镜像源加 `RUNSC_SHA512=skip`；`INSTALL_RUNSC=0` 可跳过）+ 沙箱运行环境（系统 python3 预装库 → 见代码 `apps/server/agentcore/tools/sandbox/cloud_python.txt`，Dockerfile `-r` 安装、工具描述同源读取；`fonts-noto-cjk` 中文字体，nodejs）。正常 `pnpm deploy:backend <sha>` 构建即含。
2. **配置**：`deploy/config/production.env` 护栏 `GVISOR_*`（可跟 `production.env.example`；**`GVISOR_TIMEOUT_MAX_SECONDS` ≥1230**）。默认已开，无需再写 `GVISOR_ENABLED=true`（example 已写 true）；紧急才设 `false`。
3. **编排**：`deploy-server.sh` / `finish-server.sh` **默认**叠加 `deploy/docker-compose.sandbox.yml`（显式 `GVISOR_ENABLED=false` 才跳过）。活栈目录（`AGENTCORE_DEPLOY_DIR`）若缺该文件，finish 脚本会回退到仓库 `repo/deploy/docker-compose.sandbox.yml`。**宿主前置**（Ubuntu 24.04）：`kernel.unprivileged_userns_clone=1`（或等价 sysctl）；`kernel.apparmor_restrict_unprivileged_userns=0`（24.04 默认 1 会拦 runsc 非特权 userns，须显式放开）。runsc 安装路径固定 **`/usr/local/bin/runsc`**（Dockerfile 下载层），**不可改路径**——宿主 AppArmor profile 按此路径附着。叠加 compose 的 `apparmor=unconfined` 姿态**无需改**。
   **sandboxd（独立服务）**：overlay 起 `sandboxd` 容器（同 api 镜像；`user: "0:0"`；`cap_add: NET_ADMIN, SYS_ADMIN`；`mem_limit: 4g`；入口 `deploy/sandboxd-entrypoint.sh`）。准备**容器私有** `/run/netns`（不挂宿主 `/run/netns`），uid 0 跑 `python -m agentcore.tools.sandbox.sandboxd`（Unix socket `/run/agentcore/sandboxd.sock` 供 API RPC，`SO_PEERCRED` 只允许 API uid；共享卷 `sandbox-run`；预览 HTTP compose 发 `127.0.0.1:8787`，勿 `0.0.0.0`）。装包 allowlist 代理在 **sandboxd 进程**（veth 主机端在其 netns）。**api 不叠 caps、不换 entrypoint、不 exec runsc/ip**；镜像 `USER app`。业务进程不是 root、无 `SYS_ADMIN`，也**不是** `privileged:true`。桌 guest（含 Chromium）固定 `--ignore-cgroups`。`sandboxd` 的 `mem_limit` 须覆盖桌上 node+Chromium；升配时抬 sandboxd 帽，不是「桌与浏览器互斥」。`./sandboxd-entrypoint.sh` 卷按**第一个 `-f` 的目录**解析，活栈目录缺文件时 Docker 会建成同名空目录。迁移 / 备份 oneshot（`COMPOSE_BASE` / `dc_oneshot`）**不叠** sandbox：长驻 `up -d` 才叠。停机迁盘前 **stop api 与 sandboxd**（guest 占盘）。
4. **发布前自检**（开发机 Windows 可跑非 live；真 runsc 须 Linux/Docker）：
   `python apps/server/scripts/verify_gvisor_sandbox.py`；镜像内：
   `python apps/server/scripts/verify_gvisor_sandbox.py --live`（见脚本头注释 Docker 用法）。**验收身份必须是生产身份**（api `USER app` + 独立 sandboxd），禁止 `--user root --privileged` 冒烟当放行。

**部署后人工验证清单**（开发机 Windows 无法跑 runsc，以下须在 Linux 自托管机上过一遍再放灰度）：

1. 启动即健康：`GVISOR_ENABLED=true` 下 api 正常起；启动日志 **`sandbox.cloud_health_ok` 为 DEBUG 级**（生产 info 级默认看不到，属正常）；**`sandbox.cloud_health_failed` 为 WARNING 级**（生产可见；`reason`/`detail` 须可读，Windows 开发机常见 `not_linux`）。故意改坏 `GVISOR_RUNSC_PATH` 仍应正常起，但日志见 `sandbox.cloud_health_failed` warning，且云对话不装配 `code_execute` / `package_install` / `browser`（能力行显示未装配）。勿再把形状 A/B 当两套执行主路径，也勿为浏览器另起第二套 runsc jail。
2. 容器内 runsc 真能跑：云对话让 AI 执行 `print("ok")` 类代码——若报「代码执行环境启动失败」，按叠加层注释排查 seccomp / userns 前置 / sandboxd socket。
3. **云浏览器**：能力行 `browser=已装配` 与执行类同一谓词（不是右坞已有帧）。云对话让 AI `browser(action=navigate)` 打开公网页 → 桌面/Web 右坞出现 Sandbox 直播帧；桌上已启的开发服务器可用 guest `http://127.0.0.1:<port>` 打开（相对 HTML / `workspace://` 仍仅 Local Bridge）。桌不健康则 `browser=未装配`。握手失败打 `browser.session_open_failed`。
4. 产物落盘端到端：让 AI 用 python-pptx 生成一份 pptx → 工作区面板能下载打开（直接写在桌上，无 copy-out）；中文内容不是豆腐块（字体）。
5. 隔离与出站：guest 内抓 **非 allowlist** 外网应失败；读不到宿主密钥 / 整份 `DATA_DIR`。包装源（npm/pypi）经桌上 chokepoint 可达。
6. 护栏生效：并发 3 个执行第 3 个在等待期后收到「执行位已满」；超时长死循环被杀；guest 不得写出当前工作区外。空闲桌（无在飞 exec / 无长驻进程 / 无沙箱 browser）过 TTL 后 guest 被 reap，下一回合 prepare/attach 再创建；有 `pnpm dev` 的桌不得被收。
7. 资源观察：灰度期定期 `docker stats` 看 **sandboxd** 容器内存（桌上 node+Chromium 同 jail；`mem_limit` 是运维帽，超了抬 sandboxd 帽/升配，不是拆成两套 jail）、宿主负载，用真实负载决定升配（§六）。
8. **服务端 git**（与 gVisor 正交，任何机器都要过）：云工作区对话能力行 `git=已装配`，启动日志无 `git.binary_unavailable` warning。镜像缺 `git` 时进程照常起、只**静默**不装配 git 工具（AI 的 `git` 与用户「从 GitHub 克隆」一起失效，界面上只表现为「AI 不会用 git」）——更新了代码却没重建镜像的部署尤其要看这条。

> **状态**：第一刀已切流（独立 `sandboxd`、回合外开通、默认开）；紧急关闭用机上 `GVISOR_ENABLED=false`；健康失败则诚实不装配。⏳ 第二刀用户预览须生产配 origin 并用上才算落地（换票与 sandboxd HTTP 存在；空 origin → mint 503）→ [安全权限与治理 · §五 代码执行沙箱](/docs/05-平台与运维/安全权限与治理.md)。

### ⏳ 开放容量问题

- **是否升级服务器规格**：多 Agent 并发 + 沙箱升级可能需要更多资源；放量前按实际负载评估（约 2C8G 量级通常够 MVP）。

### API 进程约束：多 worker 一律拒启

`WEB_CONCURRENCY` / `UVICORN_WORKERS` / `AGENTCORE_API_WORKERS` > 1 → **启动拒绝**（DEBUG 仅强警告，日志 `deploy.multi_worker_refused`）。`python -m agentcore` 默认 `workers=1`。

拒的是**进程内单例**，不是限流：账本队列已迁共享 Postgres `cost_ledger_outbox`（每进程可自 drain）、`RATE_LIMIT_BACKEND=redis` 也已共享限流器，但另有两处没有共享后端可切——

- **设备履约中枢**（`fulfill/hub.py`）：桌面履约 SSE 连在 worker A、回合跑在 worker B，B 查不到任何履约方（本地工作区 / Host / MCP / 白板全断），本地工作区回合更被在场闸判成「本机桌面未连接」直接硬拒。
- **对话事件流**（`runtime/turn/runs.py` · `runtime/events/conversation_hub.py`）：attach / 跟播落到没跑该回合的 worker → `follow=false` 恒 204、`follow=true` 拿到一条永远只有心跳的空流。**这条是静默的**——客户端分辨不出它和「对话真空闲」的区别。

即使配了 `RATE_LIMIT_BACKEND=redis`，多 worker 仍拒启：校验含履约中枢与跟播，不只限流与账本。→ `_validate_single_process_assumptions`。**否决**以为共享限流/账本就可以开多 worker。

**放开的前置是跨进程扇出（⏳），不是任何环境变量**——故有意不留 opt-in 逃生阀。

**诚实边界（勿宣称全面多机就绪）**：单 worker 也不等于就绪——审批门、IM、steer、journal settlement 同样是单进程姿态；journal 共享存储分期不做。

## 八、配置分层与种子数据 ✅ 已确定

### 8.1 启动依赖层级

| 层级 | 服务/配置 | 失败行为 |
|---|---|---|
| L0 硬依赖 | PostgreSQL | 启动失败；运行时 `/readyz` HTTP 200/503 **仅看 DB** |
| L0 部署栈（限流） | Redis（`RATE_LIMIT_BACKEND=redis` 时 compose 必带） | 部署需就绪；运行时限流可 fail-open；`/readyz` 仍探测并写 body `redis`（软依赖，不因 Redis 回 503） |
| L0 生产硬约束 | `JWT_SECRET_KEY`(非默认/非空)；`billing_mode=byok` ⇒ `ENCRYPTION_KEY`(64 hex，非空且合法)；`COOKIE_SAMESITE=none` ⇒ `COOKIE_SECURE=true`（桌面端 `app://` 跨站 cookie 前提）；**多 worker 一律拒启**（跟播 / 履约中枢无跨进程扇出，redis 也不放行；见 §六） | `RuntimeError`（fail-closed，启动即拒） |
| L1 软依赖 | NATS, MinIO, 搜索引擎, 云沙箱健康探测（runsc / subprocess） | 警告后继续，相关功能降级（沙箱不健康 → 执行类工具整类不装配） |
| L2 运行时 | LLM_API_KEY, Embedding | API 可运行，调用时失败或跳过 |

**设计原则**：关键安全配置走 fail-closed（缺失即拒绝启动），功能性配置走 fail-safe（降级但不崩溃）。

### 8.2 环境变量分层

两个 `.env` 文件明确分工（**均不入仓、均在服务器人工维护**；`pnpm deploy:backend` / `finish-server.sh` **只读**应用 env，部署时仅改写其中的 `IMAGE_TAG`）：

| 文件 | 内容 | 消费方 |
|---|---|---|
| `$AGENTCORE_HOME/.env` | ACR 登录（`ACR_USERNAME` / `ACR_PASSWORD` / `ACR_REGISTRY`）；可选 `AGENTCORE_HOME` / `AGENTCORE_DEPLOY_DIR` 覆盖 | `finish-server.sh` · `deploy-server.sh` · `healthcheck.sh` |
| `$DEPLOY_DIR/config/production.env` | 应用运行配置（JWT / `ENCRYPTION_KEY` / `PLATFORM_*` / **SMTP 七项** / CORS / 配额…）；`POSTGRES_PASSWORD` / `REDIS_PASSWORD` 供 compose 插值 | compose `--env-file` **与** api 容器 `env_file`（`docker-compose.app.yml`） |

默认 `$DEPLOY_DIR` = `$AGENTCORE_HOME/repo/deploy`。模板 → [`deploy/config/production.env.example`](/deploy/config/production.env.example)；真值文件 → `deploy/config/production.env`（`.gitignore`）。DB/Redis 连接串在 `production.env` 仅占位（`127.0.0.1`），由 compose `environment` 覆盖为服务名（`postgres` / `redis`）。

**首次 / 补配 SMTP（开放注册）**：① 在 DirectMail（或其它 SMTP 服务商）完成发信域名的 SPF / DKIM / DMARC / MX；② SSH 到生产机，编辑 `$DEPLOY_DIR/config/production.env`，自模板复制段填入 **`SMTP_HOST` `SMTP_PORT` `SMTP_USERNAME` `SMTP_PASSWORD` `SMTP_FROM_ADDRESS` `SMTP_FROM_NAME` `SMTP_TLS_MODE`**（勿提交 git）；③ `docker compose … exec api python scripts/verify_smtp.py <你的邮箱>` 真发一封自检；④ `docker compose … up -d` recreate api（或 `finish-server.sh <当前 sha>`）；⑤ 查 api 日志无 `email.smtp_unconfigured_registration`，再烟测 `POST /v1/auth/register/send-code`。细节 → [认证与会话 · §九](/docs/05-平台与运维/认证与会话.md)。

### 8.3 种子数据与确定性 UUID

使用 **UUID v5** 确定性生成种子实体 ID：`uuid5(NAMESPACE, slug)` → 同一 slug 永远同一 ID → seed 脚本幂等安全。→ 见 seed 脚本。
