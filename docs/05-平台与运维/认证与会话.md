# 认证与会话

> ✅ Phase 1–2 已落地（刷新宽限 + 前端单飞；桌面 `app://` 跨站 cookie；CSRF HMAC 强制；Bearer 手机豁免）。✅ 邮箱验证注册 + 找回密码（先验后建，见 §四）+ 邮箱或用户名登录（见 §一）。
> → `apps/server/agentcore/auth/`、`api/routes/auth.py`、`mail/`

## 一、设计基线

| 维度 | 选择 | 理由 |
|---|---|---|
| 登录标识 | 邮箱**或**用户名 + 密码 | 输入含 `@` 走邮箱、否则走用户名；故用户名禁含 `@`（`@` 就是判别位）。**已撤销「邮箱不作登录标识」**——那条成立于 `email` 可选可空时期，邮箱必填必验后，「用邮箱注册却要用用户名登录」是断裂体验。用户名仍受理不是过渡期，而是给存量 `email` 为空的账号永久兜底。登录字段名仍叫 `username`（改名要连带三端 + admin + 生成类型，只换命名美观） |
| 令牌传输 | httpOnly Cookie | JS 拿不到明文；SSE/fetch 天然带 |
| 令牌载体 | access（短）+ refresh（长，path 限 auth） | 减小 refresh 暴露面 |
| 密码哈希 | argon2id | 规避 passlib+bcrypt≥4.1 坑 |
| 注册 | 开放 + 邮箱验证码（同页），必填**邮箱 + 密码**，**昵称选填**（`REGISTRATION_OPEN` 可关） | 被否：邀请码——摩擦大。**先验后建**：`users.email` 唯一，若先建未验证账号，他人邮箱会被永久占住（squatting）。三层拆开：邮箱 = 登录/找回；昵称 = 露脸（不必唯一）；用户名 = 找人码。用户名**不在注册时由用户填**，后端生成中性句柄（`user_` + 8 位 hex），登录后经 `PATCH /me` 认领（系统句柄随时可改成自选；自选后 14 天冷却）。**被否：从邮箱前缀派生**——用户名经 `PersonPublic` 对外暴露，派生等于公开用户邮箱前缀。**被否：注册必填/选填用户名**——开号时多数人不知道这是搜人用的。**被否：昵称全站唯一 / 用邮箱或昵称搜人**。昵称选填进注册（`register/verify` 的 `display_name`）：开号即进全员群，露脸不能拖到设置；空着则昵称先等于系统句柄。滥用事后治理靠限流 + admin 停用（见 §二·可查） |
| 验证码 | 6 位数字，TTL 10min，错 5 次作废，一次性，只存哈希 | 被否：magic link——桌面端要处理 deep link，比输 6 位数字麻烦；且邮件客户端的安全扫描器会提前「点掉」链接 |
| 暴力破解 | 5 次锁 15min | |

客户端注册一张表：邮箱、密码、验证码（右侧「获取验证码」）、昵称（选填）、年满 18、协议/隐私；主按钮「注册」。昵称在验证码下方、勾选上方；不填不拦开号。API 仍是 `send-code` → `verify` → `login`，先验后建不变。**获取验证码**只校验邮箱 + 密码（发码接口就要密码）；昵称只在 `verify` 提交，改昵称不必重发验证码。两项勾选拦的是开号，不拦发码。邮箱或密码在发码后改过必须重发（pending 存的是发码时的密码哈希）。两项**刻意保持独立勾选**（国内同类产品多合并为一个）：分开勾选留下「用户单独声明过年龄」的举证链，合并进协议正文会弱一截；减重只做视觉收紧，不合并语义。提交按钮**不做静默禁用**——逐字段说明缺什么，「按钮灰着却不说原因」是反模式。忘记密码仍两步（本轮不动）。Schema 真相源 = ORM + alembic。

用户名（找人码）规则：3–32 位，入库小写，`a-z` `0-9` `_` `.` `-`，首尾须字母或数字；禁 `@`（登录判别位）；禁 `user_` 前缀（留给系统句柄）；保留 `admin` / `official` / `agentcore` / `support` / `system`。占用与登录均大小写不敏感。搜人仍精确用户名或精确用户 ID，不搜昵称、不搜邮箱。

## 二、数据模型

→ `db/models/auth.py`、`users.py`：`users`（`email_verified_at` 是时间戳而非 bool，未验证为 null——省一个字段还多一份「何时验的」；`username_changed_at` 自选用户名冷却，系统句柄为 null）/ `credentials` / `refresh_tokens`（只存哈希）/ `pending_registrations`（验证前的注册请求，含密码哈希——先验后建的落点）/ `email_challenges`（码哈希 + 尝试次数）。邀请码表 `invites` **已退役**（开放注册后不再发码/验码）。密码与 refresh 均不可逆；建模约定见 [核心接口 §6.2](/docs/02-架构/核心接口定义.md)。

### 加强可查（同人多号 · 观测面）✅

目标：**先看见再谈拦**——让运营能在 admin 里按 IP / 注册时间簇关联多账号；本轮**只加强可查**，不加防薅硬闸。

| 信号 | 落点 | 语义 |
|---|---|---|
| `users.registration_ip` | 注册请求写入（`get_client_ip`，与限流同源） | 开号时出口 IP；**旧账号可 null**（迁移只增可空列，不回填） |
| `refresh_tokens.ip` / `user_agent` / `client_platform` 等 | 登录 / 刷新签发会话时写入 | 事后登录出口与客户端面；admin 详情只读展示 |

运营查「是不是同人多号」的主路径 → [管理员后台](/docs/05-平台与运维/管理员后台.md) 用户名册按 IP（注册 IP **或**任一会话 IP）+ 注册时间窗筛选，详情看 `registration_ip` 与会话元数据。

**本轮明确不做**（边界）：不停用/封 IP、不加图形验证码（CAPTCHA / Turnstile）、不加一次性邮箱域名黑名单、不做 Gmail 点号 / plus 别名规范化后查重、不按同 IP 硬拒注册、不做设备指纹 / 同人多号硬上限、不恢复邀请码、不改开放注册姿态。滥用事后治理仍靠 **Auth IP 限流 + admin 停用/改配额**（既有口径）。更宽的滥用防护蓝图仍 ⏳ → [安全权限与治理](/docs/05-平台与运维/安全权限与治理.md)。

**邮箱验证码（§四）不是防薅闸**——立项理由是解锁找回密码 + 账号可触达，不是拦注册；真人拿一次性邮箱或 Gmail 别名照样反复开号。它对防薅的唯一贡献是把 `email` 变成了**可风控字段**（此前产品注册路径根本不收邮箱，黑名单与规范化无从下手），而那两项仍未做。真要限制免费额度滥用，手段是把额度绑到更贵的身份（手机号 / 支付方式 / 有账龄的 OAuth），不是邮箱。

## 三、令牌模型

| 令牌 | 形态 | 生命周期 |
|---|---|---|
| access | 无状态 JWT（HS256；`fam`=token_family） | 默认 30min |
| refresh | 不透明随机串（库存 SHA-256） | 默认 30d 滑动 + 族绝对上限（默认 90d；admin audience 默认 24h；`persist_session=false` 族默认 8h） |
| inference | 无状态 JWT（`type=inference`） | 默认 12h；仅 `/v1/inference/*` |
| folders | 无状态 JWT（`type=folders`） | 默认 12h；仅账号 folders 窄面（`GET/POST /v1/folders`、`GET/DELETE /v1/folders/{id}`、铸票 `POST /v1/folders/token`）。`DELETE` 只到**软删**（供 sidecar CEO 的 `delete_folder`）；不可逆的 `DELETE /{id}/permanent` 仍限 access，不进窄票 |
| account | 无状态 JWT（`type=account`） | 默认 12h；仅 account 引擎窄面（对话日志 `POST /v1/account/conversations/search|read`、规则 `…/rules/list|remember`（list 含 always + on_demand 正文，供 sidecar 按需目录 / `consult`）、记忆 `…/memory/{list,load,save,delete,project-scopes}`、铸票 `POST /v1/account/token`） |

access / inference / folders / account **类型互斥**（错 type → 401）。桌面 sidecar 持 `{baseUrl, apiKey}` 形的 inference / folders / account 窄票，**禁止**把 access 塞进 sidecar。

access 纯本地解码；无效一律 401。会话元数据写在 `refresh_tokens`（含 `persist_session`、`ip` / `user_agent` / `client_platform`）；终态行 GC（默认保留 7d）。运营可查同人多号时复用这些字段（§二·可查），不另起审计表。

`LoginRequest.persist_session`（默认 `true`）：`true` = 持久 Cookie + 长 refresh；`false` = **session cookie**（无 Max-Age/Expires，关浏览器即丢）+ DB 侧更短绝对上限（`EPHEMERAL_REFRESH_FAMILY_MAX_HOURS`，默认 8）。Bearer `/token` 共用同一字段——`false` 仍发 token，但 `refresh_expires_in` 为短 TTL（客户端不应持久化）。MFA pending JWT 携带该标志，验码后 cookie/TTL 策略不变。

**客户端产品口径**（不做应用内「记住密码」；密码交给系统密码管理器）：
- 桌面 / 手机：默认长期会话（等价 `persist_session=true`），登录页无「保持登录」勾选；仅本地记住用户名。
- 管理端：登录页「保持登录」默认不勾（传 `false`）；勾选才持久。冷启动对过期 access 静默 refresh（与桌面对齐）。

## 四、端点契约

`POST /v1/auth/{login,refresh,logout,change-password}` + `GET/PATCH/DELETE /me` + 会话管理；头像在 `/v1/users`。字段 → OpenAPI / `api/schemas/auth.py`。

**邮箱验证面**：注册 `register/send-code` → `register/verify`（201 但**不设 cookie**，客户端接着自行调 `login` / `token`）；找回密码 `password/forgot` → `password/reset`（成功吊销全部 family，并盖上 `email_verified_at`——收到码即证明收件箱）；登录态补验 `email/send-code` → `email/verify`。发码一律 202 `{status, expires_in}`，`expires_in` 是**验证码 TTL（600s），不是重发冷却**（冷却 60s 在限流侧，客户端别拿它当倒计时）。`send-code` 在发码**前**就校验邮箱占用与密码强度，免得用户验完码才发现邮箱已注册；它只收 `email` + `password`，多传 `username` / `display_name` 会被忽略（不 422），拿不到自选用户名。昵称走 `register/verify` 的可选 `display_name`（空白视为未填）。即时建号 `POST /v1/auth/register` 默认 410 → `LEGACY_REGISTER_ENABLED`，**与 `DEBUG` 解耦**：为排查打开 DEBUG 不得重开未验证注册入口。`PATCH /me` 可改昵称（`display_name`）、邮箱、用户名；改邮箱会清空 `email_verified_at` 且不自动发码。用户名认领占用则 422；系统句柄可随时改，自选后 14 天内再改同样 422。

**决策语义**：login 401 不区分账号是否存在；非属主会话 → 404；`revoke-others` 无 `fam` 旧 access → 422（不选 revoke-all 防误踢自己）。改密吊销全部 family、当前会话重发 Cookie。注销：软删+匿名化+跨域清理（对话/分享/BYOK/头像）；账本保留。

`password/forgot` **恒 202**，SMTP 故障也不例外（失败只记 `email.send_failed`）——否则「已注册返 422 / 未注册返 202」会把这个端点的全部不透明性打穿。`register/send-code` 与 `email/send-code` 反之，发信失败返 422 让用户能重试：前者本来就用「邮箱已占」告知占用状态（**注册面天生可枚举邮箱**，业界通例，靠限流抬成本而非藏），后者是登录态验自己的邮箱、无枚举面。未验证登录：`REQUIRE_EMAIL_VERIFIED` 默认 **false**（存量账号 `email_verified_at` 为空必须能照常登录），打开后返 403 `EMAIL_NOT_VERIFIED` 而非 401，客户端才能区分「密码错」与「去补验」；**不加强制拦截页**（桌面 / 手机无此页面框架，为存量用户新建三端拦截页不划算）。

**头像**：独立 `AssetStorage`；内容寻址键 + `?v=<hash>`；取图公开（`<img>` 不带 Cookie）；上传需 `AuthUser`。IM 人侧 DTO（`PersonPublic.avatar_url`）复用同一派生 URL，不是第二套存储；会话列 `chats.avatar_url` 是群徽 / 官方号预留，与用户头像无关 → [消息 IM](/docs/05-平台与运维/消息IM.md)。

**Bearer（手机）**：`/v1/auth/token*` 返明文、不设 Cookie。Capacitor Android origin = `https://localhost`——生产 CORS 必须含之（及 `capacitor://localhost` / `http://localhost`）。注入：`AuthUser` / `OptionalUser` / `AdminUser`。

## 五、刷新轮换 + 重用检测

| 场景 | 行为 |
|---|---|
| 首次交换 | 标 `rotated_at`、同 family 签发后继 |
| 已 rotated 在宽限窗（默认 10s）内再现 | 善意并发 → 补发、**不撤销** |
| 超窗 / 已 revoked 再现 | 吊销整个 family |
| 过期 | 拒绝 |

前端单飞刷新（renderer + 主进程协调）。刷新三态：`renewed` / `auth_dead`（仅 401/403）/ `transient`（网络/5xx → **不踢登录**）。AuthGate：`loading` / `unavailable` / `unauthenticated`。

## 六、静默刷新约束

401→刷新→重试对用户无感。**流式通道须各自接入**（聊天 SSE 常绕过统一封装）；新增绕过统一层的 fetch 通道同理。

## 七、Cookie / CSRF 易踩坑

- **refresh path**：生产反代 `/api/` → `COOKIE_PATH_PREFIX=/api`，否则 cookie 不回传。
- **cookie 作用域按 API 主机、不按页面 origin**：不设 `domain=` → host-only，落在**被访问的 API 主机**上，`path=/`。两个 web SPA 只要指向同一 API origin 就共用 access cookie，页面分域也没用，后登录者顶替先登录者（对方 `/me`、`/sessions` 全读到，写也落对方账号）；此时 CSRF 报 `signature_mismatch`，403 不再回发新 token（否则用户重试一次就以对方身份写成功），前端也据此不重放。**`/me` 发票后这道拦不再兜底**：被顶替的 SPA 一旦 reload，冷启动就会拿到一枚绑新主人的 token，写直接落到对方账号。**不为此在 CSRF 层加特例**（让 `/me` 判 mismatch 再决定发不发）——当前生产 cookie web 只留 `app.` 同源一套（与 API 同主机，不是第二页面 origin）。**不要**再挂 `m.` 当第二套 cookie SPA——会互顶会话。Capacitor 壳走 Bearer；admin 已分到自己域的 `/api`。将来若真出现第二个 cookie 页面 origin，修法仍是分域。故 admin 走自己域的 `/api` → [管理员后台 §二](/docs/05-平台与运维/管理员后台.md)。桌面 Electron 有自己的 cookie 分区、原生壳走 Bearer，均不受影响。
- **生产桌面**：`SameSite=None` + `Secure`（`app://` 跨站）；启动 fail-closed（none 而无 Secure → 拒启）。SameSite **不**提供 CSRF 防护。
- **CSRF**：无状态 HMAC（`sign_csrf_token`），**勿改回服务端存储**（热重载/多 worker 会清空 → 403 CSRF_FAILED）。下发**只有四处**：登录、续期、`GET /v1/auth/me`（仅当该请求以 cookie 会话到达——口径与拦截侧一致，看 access cookie 而非客户端可自选的 header；纯 Bearer 不发）、以及「写请求因没有可用 token 被拒」的那条 403 自带补发。**勿改成每个响应都盖章**——这枚 token 寿命等于刷新窗口且不可吊销，铺到每个 GET / 每次 SSE 重连就等于洒进代理访问日志、用户导出的网络记录与错误上报面包屑，而客户端本来就能靠「重试那一条被拒的请求」自愈。`/me` 是后补的第四处，因为冷启动只凭 access cookie 续命时 login 和 refresh 都不走，它是唯一能武装会话的响应。**桌面端连「续期」这一处都从未生效**：renderer 把静默刷新委派给主进程走纯 Bearer `/v1/auth/token/refresh`，补发的握手落在一个没有 cookie 会话、也无法把响应头传回渲染进程的地方——所以在 `/me` 发票之前，桌面端每次冷启动的第一条写请求都必吃 403（实测 `POST /v1/conversations` + `reason=missing`）。仍有的 403 由两端 `api.*` 统一层自动重放一次，**判据只看这条响应有没有带回新 token**（后端算好的「可自愈」裁决，客户端不从状态码或文案二次猜测）；不带 token 的（`signature_mismatch`）不重放、照常报错。绕过统一层的裸 fetch（SSE 回合流 / 上传 / workspace 文件）不重放，只武装下一发——流式 POST 上重放有重复副作用风险。仅走响应头，无 CSRF cookie（曾有一个非 httpOnly 的，后端从不读、跨源前端也读不到，已删）。放行面只有四类：`csrf_enabled=false`（勿关；关了只大声告警仍启动）、安全方法、豁免前缀（登录/注册/刷新/token/hooks/shared）、无可解码 access cookie（纯 Bearer 手机端即属此类）。
- **主进程 outbox**：纯 Bearer、`credentials:omit`；写回 cookie 须按 API URL 推 SameSite/Secure，refresh 须带 `expirationDate`。
- **CORS**：`CORS_ALLOW_ORIGINS` 逐源；含 `app://agentcore` + Capacitor localhost。`m.` 发版 301 / 撤站后从列表去掉。

排障：「总掉登录」先查刷新链路，勿只调长 access TTL。桌面日志 `userData/logs/desktop.jsonl`：`auth.bootstrap` / `auth.session_kicked` / `auth.refresh`。

## 九、配置

生产必改：`JWT_SECRET_KEY`；`COOKIE_SECURE` + 跨站 `COOKIE_SAMESITE=none`；**开放注册时**齐 **`SMTP_HOST` `SMTP_PORT` `SMTP_USERNAME` `SMTP_PASSWORD` `SMTP_FROM_ADDRESS` `SMTP_FROM_NAME` `SMTP_TLS_MODE`**（写在 `$DEPLOY_DIR/config/production.env`，见 [部署拓扑 · §8.2](/docs/05-平台与运维/部署拓扑与环境.md#82-环境变量分层)）。本地对照 → `apps/server/.env.example`；生产模板 → [`deploy/config/production.env.example`](/deploy/config/production.env.example)。

**发信**：通用 SMTP，**无厂商 SDK**——换阿里云 DirectMail / 腾讯云 SES / SendCloud 只是改上述七项。**未配置 = 静默降级**：DEBUG 把验证码打进日志（本地开发即靠这个跑通全流程），非 DEBUG 只记 `email.unconfigured` 且**不挡注册**（`send-code` 仍 202，用户永远收不到码）；启动期打 `email.smtp_unconfigured_registration` 警告。发信域名（建议 `mail.` / `notify.` 子域，勿与企业邮箱共用主域）须先配好 SPF / DKIM / DMARC / MX 并在服务商侧验证通过，否则 SMTP 连得上也发不出去；阿里云 ECS 封 25 端口，用 465(ssl) 或 80/587(starttls)。机上验收 → `docker compose … exec api python scripts/verify_smtp.py <邮箱>`（`apps/server/scripts/verify_smtp.py`）。

**发码限流**独立于 Auth IP 限流（两者叠加生效）：同邮箱 60s 冷却 + 每日 8 次，同 IP 每小时 20 次。护的是发信域名信誉——没有按邮箱维度的冷却，接口就是个对着任意第三方邮箱的轰炸器，收件人一举报垃圾邮件就毁掉整个域名的送达率。
