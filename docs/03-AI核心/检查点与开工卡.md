# 检查点与开工卡

> **权威**：`ask_user`、`team_preview` / `plan_review` / `stage_card`。挂起机制 → [运行时三模型](/docs/03-AI核心/运行时三模型与挂起.md)；编排字段 → [编排器](/docs/03-AI核心/编排器与CEO主Agent.md)；前端卡 → [协作图 UX](/docs/04-前端/协作图与双视图UX.md)。
>
> **主循环归属**：「**拍**」的产品权威——哪些时刻值得停下来问用户 → [主循环](/docs/01-产品/产品定位与品牌.md)。

## 一、`ask_user`（通用澄清）✅

**定案（已落地）**：取消「开场 / 开工提案」产品位与场面账；`ask_user` 仅为 CEO 在 ReAct 循环中的**通用澄清步**（可与检索/读文件等任意穿插，可连续多次）。参照通用 Agent（Cursor / Claude Code 式），非垂直生成器式选项闸。

**产品原则（挡路拍板）**：用户需求是「该聊就聊、必须拍板时再冻回合」——不是多一种问卷。判据与呈现：

| 原则 | 口径 |
|---|---|
| **挡路才问** | 没有答复，Agent 是否**不能**负责任地做下一步？不能 → 可 `ask_user`；能（含「先按合理默认聊/做，错了再改」）→ 不当检查点 |
| **冻结要贵** | 阻塞挂起打断心流、占住回合；只在拍板价值高于打断成本时用。软偏好、继续共创 → `end_turn`，球留在输入框 |
| **桌上结果未定 ≠ 一律发卡** | 「讨论类开场」三选仅当请求**可能**变成组队摸清 / 成文、且形态真会影响编制时。桌上结果已是对话本身（共创、审美对齐、闲聊式探讨）→ 正文推进，不发卡 → [编排器 · 团队形态](/docs/03-AI核心/编排器与CEO主Agent.md) |
| **选项服务动作** | choice `label` 对齐下一步会做什么（交付档、调研主体、手段/授权等）；**禁止**把正文已摆出的候选菜单再投进卡里催偏好收敛 |
| **聊天续聊 ⊥ 检查点** | 续聊＝普通气泡 + 输入框；检查点＝冷卡提交/取消。礼貌追问、脑暴后「你更倾向哪个」属续聊 |

| 项 | 决定 |
|---|---|
| 开场仪式 / kickoff 味 UX / 提案体硬闸 | **取消** |
| 澄清方式 | 多轮短问；**Agent 自主**决定何时问、问什么（须符合上表挡路原则）；交付类建议选项写**桌上结果**（一页先上 / MVP 主流程 / 模块流水线等），不写编制名单；选档后由 CEO 填 `playbook_args.intensity`（→ [编排器 · 团队形态](/docs/03-AI核心/编排器与CEO主Agent.md)） |
| 「就这样开做」开场主 CTA | **不作为**产品主路径 |
| 场面账（`style_options` / `format_options` + 风格/演讲/自动化硬门禁） | **取消**；缺信息靠短问，错了再改。点名载体/手段次优时的顾问短问 ≠ 复活场面账 → [编排器 · 载体/手段顾问](/docs/03-AI核心/编排器与CEO主Agent.md) |
| `team_preview` | **不动**（组队确认 ∪ 能力授权，与 ask 正交） |

**统一机制**：单一 `ask_user` 工具；调用即冻回合。阻塞检查点 = 挂起即收口，冷路 `POST …/resume`。「该结束还是挂起」归运行时。答案不要紧就在回复里写明假设、不出卡。不挂住全场的提问走 `escalation`（不挂起回合、兄弟继续跑）。浏览器需用户登录时 CEO 设 `browser_login=true`（与 worker `escalate(browser_login)` 同形「需要你登录 / 已登录，继续」卡，**禁止**把完整 escalate 开给 CEO）。

**Live 出卡（桌面 ✅）**：挂起可操作面只靠 ResumePrompt ← InteractionStore cold pending（时间线挂起态不画标记，对齐 ask_user）。`*_required` 入 IX 后须能出卡；`serverMessageId` stamp 晚到则 rebind 立即补画——**否决**靠硬刷新 journal hydrate 才看见。第二轮 / 同会话再次冷挂起：新 host 上真实 `*_required` 可替换已结算墓碑；同 host 重放仍挡。手机 ResumeCard 各自实现（`coldInteractions` / `coldResume`），语义对齐。→ 见代码: 桌面 `stores/interactions/store.ts` · `services/resume.ts` · `ResumePrompt.tsx`；手机 `lib/coldInteractions.ts` · `lib/coldResume.ts`

**冷卡终态权威（桌面 ✅）**：checkpoint 一旦在服务端结算，**客户端任何路径都不得把它翻回 pending**。可点性收敛到单一判据 `isColdCheckpointSettled`（本会话已观察过结算 / IX 条目已 resolved·orphaned / 消息 journal 有配对 `*_resolved`），由 `reopen` 与画卡闸 `selectVisibleColdResumes` 共用：传输失败只表达「连接断了 / 重连中」，不表达「卡又待答」，已结算的冷卡维持 `submitting`；未结算的冷卡（如 sidecar probe 失败）仍回 pending。`upsertRequired` 重放与 `message_end(paused)` 合成壳照旧写 store，但已结算的画不出可点卡——**否决**在这三条复活路径上各加一道防守（同一根因改 ≥3 层即触补丁绊线）。个案 2026-08-18 cid `513d8c06-…`（trace `ad1db7c4…`）：后端 16:35:27 即 `team_preview_resolved`、全程 `paused_count=0`，桌面 16:43 起 40 秒内对同一 turn 全量 attach 重放 4 次，终稿落库后仍反复画出「预计 2 人开工」可点卡。→ 见代码: `stores/interactions/coldSettlement.ts` · `stores/interactions/store.ts` · `services/resume.ts`

**本机引擎须自证终态（✅ 2026-08-19）**：上条三条判据里，硬刷新（Ctrl+R）后**只有**「消息 journal 有配对 `*_resolved`」是持久的——引擎必须真把它写出来，桌面才有得可判。云端 resume 在 `claim_paused_turn` **之前**把 `*_resolved` prewrite 进同一 `message_id` 的 `turn_journal`，写失败即 500 且不消耗帧。本机（sidecar）此前只写本地 Outbox，而 pause 已把该记录封成 `READY`（`mutate` 遇 READY 直接返回），于是 resume 之后的全部事实（`*_resolved`、`run_started`、finalize 整段替换）都进不了 PG：硬刷新**必然**把已开工的卡画回 pending，协作图被同一份 pending 按住（图闸口径 → [协作图 UX](/docs/04-前端/协作图与双视图UX.md)），按钮回落成发送。故「卡复活」与「图不出」是**同一根因的两个表现**，不是两个缺陷。定案三件：resume 解封 Outbox；`persist_turn_journal` 增**显式** `replace` 语义——只有持完整权威前缀者（本机 resume 重写 / outbox 写回）用前缀区间替换（只覆盖本快照占用的 live-band seq，迟到的更高 seq 天然保留），salvage 与云端渐进写入仍 insert-if-absent（否则稀疏 display 快照会清掉 append-on-emit 已占的更密行）；resume 边界补一次 best-effort 写回（失败不挡开工）。**否决**给本机 prewrite 加直写 PG——会给本机引擎引入云可达依赖，且只修卡、修不掉图与按钮；**否决**按条数/长度猜哪份快照「更完整」；**否决**在图闸另加防守（与上条同源）。本机结算另补 `paused_turn_outcomes`（`stamp_settled`，不要求已有 `paused_turns` 行），使误点旧卡得 `settled`「已被处理」而非 `regenerated` 404。个案 2026-08-19 cid `a296d88a-…`（trace `9e30066c…`）：本机 5 人审计队，回合跑完后 Ctrl+R 必现「预计 5 人开工」可点卡且无协作图。棘轮：桌面 `coldRefresh.kickoffCardResurrect.test.ts` + 后端 `test_sidecar_cold_resume_journal_gap.py`。→ 见代码: `sidecar/settlement_prewrite.py` · `conversation/store/outbox.py` · `runtime/journal/persist.py` · `db/repositories/runs.py`

**卡上 CTA（桌面/手机）**：冷卡（`ask_user` / `team_preview` / `plan_review` / `browser_login`）次要键文案一律「取消」。`ask_user`：主「提交」=`decision: continue`；次「取消」= 拒答（wire 仍 `decision: stop`）→ tool result 回灌 CEO 短续一轮（软引导收口 / 换假设；**不是**空 continue「按默认继续」；对齐开工卡取消与 OpenAI reject→resume）。**同回合连续第二次**挂起 `stop`（跨卡种累计；中间若有 continue/adjust 或新用户消息则清零）→ 系统直接 `INTERACT` 终端收口，不再起 CEO 轮（人话说明已停下 + 保留已产出正文）。取消结算桌面不占时间线「已取消」存根，问句回落为普通正文。`plan_review` / `team_preview` 三键：继续 / 调整 / 取消（`adjust` 按卡种语义不同，见 §二）。整回合协作停止（`user_stop`；界面「停止 / 已停止」）与此正交，不归本卡——**禁止**把后者 gloss 成取消。

**冷卡 × live（deferred）**：有并行 live / 宿主尚未卸锁时点继续 → 决策立刻 durability（settlement prewrite），SSE 先 `resume_deferred`，槽空后同连接续跑；卡面改「放行已记下…」。旁路发消息不取消等待。权威状态机 → [运行时三模型 · 冷 resume 与 live 交叉](/docs/03-AI核心/运行时三模型与挂起.md#冷-resume-与-live-交叉deferred)。

**何时不用**：简单问答直答；信息已够 → 直接干 / `delegate`；能按合理默认续聊或推进 → `end_turn`（偏好留给用户下一条）；意图都复述不出 → 可先正文澄清，或短 ask——不搞开场提案墙。

**否决**：开场问题墙；独立 `kickoff` 工具；场面硬账门禁；ask 与 `team_preview` 并成超级卡；多步 Wizard；为单次失败 case 写场景黑名单 / 话术剧本（靠上表原则，不扩意图分类器）。

**现状**：桌面/预览前端统一为通用澄清壳（`AskDecisionBody`）。后端普通 ask intent 默认 `decision`；场面账（`style_options` / `format_options`）**已退役**，不再出现在工具 schema / SSE / resume wire。建站无风格时 `design_prompt_block` 软注入 `s_default`（营销/工具台分域正向配方）+ copy「视觉 thesis / 信息架构」软验收；`web_quality_scan` 仍查 DESIGN.md「用户选定风格 id」。→ 见代码: `CheckpointCard.tsx` · `tools/builtin/ask_user/`、`runtime/runs/website_style.py`、`playbooks/build_site.py`

**建站品味（2026-08 复审）**：维持无场面风格卡。默认路径靠 `s_default` 配方 + thesis，不恢复 `style_options`/风格硬门（与上表否决一致）。若日后真实使用仍「同质化严重」，再议仅用通用 `ask_user` 的软短问（仍禁止场面硬账）。

## 二、检查点与团队预审

| 原语 | 触发 | 语义 |
|---|---|---|
| `ask_user` | CEO 挡路拍板（无答复则不能负责任推进） | CEO 工具效应（通用澄清，见 §一） |
| `plan_review` | step 标 `checkpoint_after` | 波间结构挂起；前置强制 CEO 把关摘要 |
| `team_preview` | `delegate`/`debate` fan-out 前 | 计划确认 ∪ 能力授权（公共 kickoff gate） |

**不答 / 超时（对齐 ask）**：默认无限等（D2 `checkpoint_timeout_seconds=None`）。卡钉在底栏 `ResumePrompt`，不因流收口 / recovery 热路空快照消失。运维若配了上限而触发 `TIMEOUT`：**不**自动开工 / 开赛、**不** grant，回灌 CEO 自行收尾（团队未启动 / 辩论未开赛）。**否决**超时静默「已自动开做」。取消仍回灌短续（与 ask 拒答同形）。

**delegate 卡**：≥2 worker，或本地 `command=kickoff` 需能力授权 → 挂卡。动作：授权并开工（可嘱咐；可**单向收紧写盘**为仅文字＝`form=prose`，不硬卸写工具）/ 调整 / 取消。**主文案**：wire `headline`＝交付档短标 + 预计人数（有 `playbook_args.intensity` 时如「MVP主流程 · 预计 3 人」；无则「预计 N 人开工」）；角色分工表为次要预览。旧帧无 `headline` 时前端按人数回退。队员行展示写盘能力标签（`可改文件` / `仅文字报告`，由 `deliverable.form` 推导）；模型身份**只读**（默认跟组合 Worker 槽；CEO/`tasks[]` 节点显式仍有效）；确认面**不展示**落座桌（同桌汇总 / 逐人芯片都不画）——worker↔桌对照对用户无拍板意义，落点走会话铬条、建桌告知、文件树/产出卡。`target_folder_*` 仍在 wire（解析与产物跟桌用）。确认面**不提供**排除岗 / 人改模入口（`excluded_run_ids` / `model_overrides` 契约可保留，与产品确认面用法解耦——编制纠偏走调整回灌或嘱咐；改模 → [编排器 · Per-worker](/docs/03-AI核心/编排器与CEO主Agent.md#per-worker-模型覆盖abc-同一功能)）。对抗视角走独立 `debate` 工具与辩论开工卡；**不**再经 delegate task 的 stance/round 展示标记挂卡或画「辩论」徽章（该假通道已收口）。→ 见代码: `runtime/kickoff/summary.py` · `runtime/kickoff/team_veto.py` · `TeamPreviewCard.tsx`  
**debate 卡**：顶层一律弹；动作：授权开赛（可嘱咐）/ 调整 / 取消。`research_first` 键已退役——「庭前取证内化」指质量前提（约定文档桥 / Evidence Pack / 发言期有界检索入台账），**≠** 庭前调查员舰队，勿再当开工前先调研关卡或代派取证员流程 → [辩论编排 §五](/docs/03-AI核心/辩论编排设计.md)。

**调整（`adjust`，delegate / debate 同形）**：不授权、不开工/开赛，`note`（必填；resume 空 note → 422）作为用户意见回灌 CEO → 由它修订方案后重新走 kickoff gate 出卡。开工闸在本回合存在**已结算但尚未兑现**的 adjust 时强制挂卡（绕过 ≥2 worker / 单人 `light` 等跳闸）；兑现 = 此后已再出过开工卡。从未 adjust 的路径不变。旧 pending 卡 `orphaned(superseded)`，**不新建循环状态机**（只加这一闸门条件）；不设轮次上限，且不计入连续取消的 `INTERACT` 收口。新卡 wire 带谱系：`revision`（首版 1）、`revised_from`（上一张 `checkpoint_id`）、`revision_note`（触发本次修订的用户意见原文）。回灌话术是修订引导（改方案后重调 `delegate`/`debate`；做不到的意见须在新方案里明说原因，禁止静默忽略），**不**套用取消的「宜先问再行动」——否则 CEO 会改弹澄清卡而非重出提案。**决策值按卡种作用域**：同一 `adjust` 在 `plan_review` 上是 steer 下游后继续，在 `ask_user` 上直接拒收；故复用 `adjust` 而**否决**新增 `revise`。代价：只看 `decision` 不看 kind 的「是否已开工」判断会误判（前端 `isKickoffGoDecision` 曾把 `adjust` 当已开工），此类判断一律按卡种区分。用户意见不进会话流，只随旧卡结算留可展开的折叠记录。→ 见代码: `runtime/kickoff/adjust_guidance.py` · `runtime/kickoff/revision.py`

**阶段推进卡 `stage_card`**：幕间一步授权（如「按此开辩」= 机制直起、`skip_kickoff`）。**否决**二步制与「发消息即 orphan」。→ 见代码: `runtime/kickoff/stage_card.py`

**跳过**（仅既有结构轴；勿新增「是否开工」意图启发式）：单 worker（计划半边不挂；能力授权半边仍可挂）；含 `checkpoint_after` 时计划半边让位；`team_kickoff=skip` 放行两半边；嵌套/`light`/续跑不挂；`stage_card` / MLR preauth 等既有机制。`team_kickoff=always` 在仍该挂的场景总挂。**例外**：本回合有未兑现的开工卡 `adjust` 时强制挂卡，绕过单 worker / `light` / 带 seed 的同回合追加续跑 / MLR preauth 等跳闸出口——任一出口放行都会让「CEO 正在重排」的等待面与队员已开跑叠在一起；`team_kickoff=skip` 仍放行（那种配置从不出卡，也就无从调整）。**禁止**把同回合已确认的阻塞 `ask_user`（`checkpoint_resolved`）当作跳开工卡条件——与 §一「`ask_user` ⊥ `team_preview`」对齐：澄清卡与开工卡正交，同回合先 ask continue 再 ≥2 worker `delegate`/`debate` 仍会挂 `team_preview`（**两种 kind 同回合**是预期，不是两张开工卡）。**一会话至多一张 pending 开工卡**：新 `team_preview` 发出前旧卡 `orphaned(superseded)`；前端可见面同口径只留最新一张。对齐「被否：两卡串联」→ [安全 · 开工卡](/docs/05-平台与运维/安全权限与治理.md)。

**专用卡**（`card` 参数，不新增 kind）：`proposal_pick` / `risk_ack` / `organize_plan` / `daily_review`（站立任务·每日复盘勾选墙）；主拍板四选一通则在提示词层。权限三轴 → [安全 §三](/docs/05-平台与运维/安全权限与治理.md)。`plan_review`/checkpoint **不受**三轴影响。
