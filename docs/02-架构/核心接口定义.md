## 一、LLM Provider 抽象层

→ 见代码：`apps/server/agentcore/llm/`

### 1.1 核心协议

LLMProvider 是 LLM 调用的统一抽象（`complete` 非流式 / `stream` 流式），实现为 OpenAI 兼容的 `OpenAICompatibleProvider`（`llm/provider/openai_compatible.py`）；多厂商经 `ProviderRouter`（`llm/provider/router.py`）按 `provider/model` 前缀路由。

设计约束（代码看不出来的部分）：
- worker 无对外模型档位词汇：CEO `delegate` 不再声明 `model_preference`；所有 worker 走单一 `agent` 画像（`agent_profile()` 无参），回合预算统一为一个上限。「力度」差异由委派协作结构（拆分 / 复审 / replan）表达，不是模型档。
- 思考模式由 `thinking` 开关控制（无思考强度参数）；DeepSeek 思考模式下 tool call 必须回传 `reasoning_content`。

### 1.2 场景画像（ModelProfile）

单一事实源：每个用 LLM 的场景（chat / agent / memory / title）都是一个命名 profile（`ProfileParams`），持有「采样参数 + ReAct 轮次预算 `max_rounds`」。**model 与 profile 解耦**——turn 级 model 由 `TurnProfiles.model` 单点解析；调用点经 `model_selection`（`select_call` / `SelectedCall` + `build_selected_request`）**已统一装配**，不在业务侧直调 `profiles.build_request`。`select_for_scenario` 为预留配对，**未**进引擎热路径。

设计约束：
- profile 是**内部实现**，不暴露给 `delegate` 调用方；所有 worker 走同一 `agent` 画像（`agent_profile()` 无参、无 per-worker 档位）。
- `max_rounds` 仅 ReAct 路径（`engine.loop`）消费；一次性 `complete` 的场景取默认。worker `agent` 画像回合保险丝统一为单一上限（默认 80）。

模型分配 / 思考开关分档 → [平台 LLM 接入](/docs/05-平台与运维/平台LLM接入.md)。

### 1.3 与其他模块的关系

→ 见代码：`apps/server/agentcore/llm/model_selection.py`（已统一策略入口：模型 × 请求参数）+ `llm/profiles.py`（场景 profile 表 / 底层 `build_request` 打包）+ `llm/resolve.py`（凭据解析）+ `llm/catalog.py`（上架/展示）。

## 三、沙箱执行（SandboxProvider）

→ 见代码：`apps/server/agentcore/tools/sandbox/`

### 3.1 实现：SubprocessSandbox / 云桌 GVisor

默认受限 subprocess 沙箱（非隔离边界，本机传统）；云端默认 `GVisorSandbox`（runsc）为 **每工作区长寿命 guest**（`tools/sandbox/gvisor.py`，Linux；紧急 `GVISOR_ENABLED=false`）。权威 → [安全 §五](/docs/05-平台与运维/安全权限与治理.md)。

**本机 subprocess**：临时目录 + `asyncio.wait_for` 超时 + stdout/stderr **2KB 分块异步捕获**（`on_output` 回调驱动 `tool_use_progress`）+ 执行后清理。

**云桌 guest**：工作区 rw-bind、uid≡`app`、桌上 allowlist 出站；`execute` 为 `exec` 进已有 guest，不是每次 copy-in/out。流式输出同 `on_output`。

**否决**：裸 subprocess 云执行（无 SEC-005 ack）；普通路径再叠 copy-in/out 例外。

## 四、API 层（前端 ↔ 后端）

→ 见代码：`apps/server/agentcore/api/`（路由 + `schemas/`；挂载见 `main.py`；OpenAPI 为前端类型唯一真相源）

### 4.1 REST API

端点与请求/响应模型的唯一真相源是 FastAPI 路由 + 自动生成的 OpenAPI（前端类型由 `openapi-typescript` 生成；路径清单见 `paths.generated.ts`，手写 URL 由 `validate_rest_paths.py` 在 `pnpm gen:types` / CI contracts 门禁对齐）。

**新建会话的幂等键（✅）**：`POST /v1/conversations` 可选 `client_request_id`——客户端为「这一次发送」自铸一个 id，重试 / 重按复用同一个。同用户同键只建一条：第二次起原样返回首次那条（仍是 **201**、body 同形，**不**报 409）。并发同键靠 `(user_id, client_request_id)` 局部唯一索引裁决，输的那次回查首次那条返回。**省略该字段 = 旧行为**，一次请求一条，不拦不报错（老客户端照常工作）；服务端**不做**任何「同用户 / 同标题 / N 秒内」的启发式去重——只认显式键。同款模式见 IM 的 `chat_messages.client_msg_id`（[消息IM §二](/docs/05-平台与运维/消息IM.md)）。每次受理落 `conversation.created`（含 `idempotent_hit`），事件字段见 [对话日志分析指南](/docs/05-平台与运维/对话日志分析指南.md)。

> 认证路由详见 [`../05-平台与运维/认证与会话.md`](/docs/05-平台与运维/认证与会话.md)。

### 4.2 SSE 实时流

两种形态。**都要扇出**——差别在扇给谁：对话页的「对方」是服务端 AI、回复由 POST 造出，但同账号的第二台设备同样要看到（多端同权），扇出面是**你自己的各端**；消息页的「对方」是另一个人的客户端，扇出面是**对端的各端**。（旧口径「对话页 POST 即可造出回复、故无需扇出」只问了「回复从哪来」，没问「谁要看」——已作废。）

- **对话页（找 AI）**：`POST /v1/conversations/{id}/messages` **恒返回** `text/event-stream`（发送即有流）；第二台设备走 `GET /v1/conversations/{id}/stream?follow=true` 跟播（空闲会话也挂得住；同一回合可多端同时跟播）。请求体 ✅ **`delivery: "steer" | "queue"` 必填**（缺 → 422）。排队取消 `POST …/queued-turns/{queue_id}/cancel`。Steer / Queue / Stop 语义与已知行为 → [运行时三模型 · 同对话再发](/docs/03-AI核心/运行时三模型与挂起.md#同对话再发steer--queue)。封装见 `api/sse.py`；事件 → [SSE 事件与录制回放](/docs/03-AI核心/SSE事件与录制回放.md)。
- **消息页（找人 IM）**：每用户一条长连 firehose `GET /v1/realtime`（server→client），把别人发来的消息扇出到你的所有在线连接（多端）；发送仍走 `POST /v1/messages/chats/{id}/messages`。fan-out 进程内 pub/sub（`messaging/hub.py`）；跨进程扇出 ⏳ → [部署拓扑 · API 进程约束：多 worker 一律拒启](/docs/05-平台与运维/部署拓扑与环境.md#api-进程约束多-worker-一律拒启) · [消息 IM §四](/docs/05-平台与运维/消息IM.md)。事件信封 `{ type, ... }`，P0 类型 `chat_message`；Cookie 鉴权、断连按 `last_read_message_id` 拉增量补偿（best-effort，非持久投递）。

### 4.3 核心请求/响应模型

→ 见代码：`apps/server/agentcore/api/schemas/`（路由层做 ORM→Pydantic 映射；前端 TS 类型由 OpenAPI 自动生成）。

对话页 `GET /v1/conversations/{id}/messages` 的 `MessageDetail.agent_mentions` 回放用户 `@` 团队角色芯片（与 `attachments` 分列；软点名，非硬路由）。写路径见 `messages.agent_mentions` JSONB。本机回写 `POST …/local-turns` 的 `RecordTurnRequest.agent_mentions` 同列落库（可选；旧客户端省略）。活态投影另有 `POST …/local-turns/begin|heartbeat|journal|stream-segments` / `abort`（owner Bearer；终局仍 `POST …/local-turns`）→ [双模式工作区](/docs/02-架构/双模式工作区.md)。`GET …/queued-turns` 的 `QueuedTurnItem` 同步返回可选 `attachments` / `agent_mentions`（出队本就会转发给 `stream_chat`）。运行中插话 SSE `user_interjection.agent_mentions` 供插话气泡画角色芯片（可选加法）。

### 4.4 SSE 事件类型

SSE 事件契约不在此重复定义。事件信封为 `{ type, timestamp, payload }`，语义见 [SSE 事件与录制回放](/docs/03-AI核心/SSE事件与录制回放.md)。**TS 类型 SoT** = `packages/contract-types`（桌面 `types/events.ts` 仅 `export type *` re-export；后端产出事件见 `runtime/events/`）。

### 6.1 核心表

完整 schema 的真相源是 ORM + Alembic 迁移链。

> 用户长期记忆不用独立表，改为文件树里 `ai_maintained=true` 的 rule 文件（见 [`Agent记忆与知识系统.md`](/docs/03-AI核心/Agent记忆与知识系统.md) §一、§二）。

### 6.2 数据模型架构约定 ✅ 已确定

> 从实践中沉淀的数据建模原则，指导新系统的 schema 设计。

#### 主键与引用

- 主键统一 UUID（Python `str(uuid4())`）
- **目标与现状均不使用 ORM ForeignKey**（`db/models/` 实际无 FK 声明），引用关系通过 `*_id` 字段在应用层维护——简化迁移、避免级联锁、允许跨模块松耦合

#### 软删除架构

带 `deleted_at` 字段的表采用查询层默认过滤：ORM `select` 默认自动过滤 `deleted_at IS NULL`，需查已删除数据须显式 opt-out。选择「全局 event + 按实体白名单分批」而非：
- 全局绑基类（一次反转所有表，波及大量故意不过滤的查询）
- 纯人工纪律（漏一处即静默泄露已删数据）

#### 版本体系

- Agent 用独立 `agent_versions` 表维护版本链
- 文件用 `file_versions` 表
- Team 不版本化

#### 文件模型单表设计

文件系统采用单表 + 维度收敛设计（`kind` × `role`），不拆多张领域表——单表是「文件夹 = 上下文边界、一棵树什么都能放」的物理基础。拆表会打碎统一内容树。

| 维度 | 含义 |
|------|------|
| `kind` | 节点类型（folder / document / upload / base），DB CheckConstraint |
| `role` | AI 上下文角色（rule / general / attachment 等）；`rule` 由 `ai_maintained` 区分用户规则与 AI 记忆。**⏳** 条目化后 `ai_maintained` 不再进 prompt，只服务写侧防护与 UI 审查 → [记忆 · 目标形态](/docs/03-AI核心/Agent记忆与知识系统.md) |

非树资产（头像等）剥离到独立 asset 模块（不在树、无 parent_id 语义）。

#### JSONB 策略

JSONB 列不盲加 GIN 索引。真正的扩展杠杆是「先用高选择性主键/外键列限定作用域 + 应用层分页」。复查触发条件：单作用域记录到万级、出现跨作用域 JSONB 查询、或特定操作符成为高频慢查询。

#### ORM 是 Schema 真相源

全部表由 Alembic 迁移链维护；以 Alembic head 为准。冷启动 = `alembic upgrade head`（建 schema）+ seed（灌初始数据），职责分离。默认值一律用 `server_default`（数据库级）。

#### 索引策略

索引随 ORM 列定义一并维护。

### 6.4 运行时状态（Redis）⏳

> **实现现状**：✅ 回合级结构化挂起/恢复已落地（`paused_turns` 表 + `runtime/suspension/` + `POST …/resume`）；✅ Turn Journal 已落地（`turn_journal` 表 + `runtime/journal/`）。⏳ Redis 跨进程检查点 / 交互队列未走 Redis——server 目前仅在 `RATE_LIMIT_BACKEND=redis` 时用 Redis 做可选分布式限流（`middleware/redis_rate_limit.py`，默认内存档）。

## 八、契约原则与交叉引用

1. 类型真相源 = 后端 Pydantic；前端由 OpenAPI 生成
2. 抽象用 `Protocol`，不用 ABC
