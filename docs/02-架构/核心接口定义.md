## 一、LLM Provider 抽象层

→ 见代码：`apps/server/agentcore/llm/`

### 1.1 核心协议

LLMProvider 是 LLM 调用的统一抽象（`complete` 非流式 / `stream` 流式），实现为 OpenAI 兼容的 `OpenAICompatibleProvider`（`llm/provider/openai_compatible.py`）；多厂商经 `ProviderRouter`（`llm/provider/router.py`）按 `provider/model` 前缀路由。

设计约束（代码看不出来的部分）：
- worker 无对外模型档位词汇：CEO `delegate` 不再声明 `model_preference`；所有 worker 走单一 `agent` 画像（`agent_profile()` 无参），回合预算统一为一个上限。「力度」差异由委派协作结构（拆分 / 复审 / replan）表达，不是模型档。
- 思考模式由 `thinking` 开关控制；DeepSeek 思考模式下 tool call 必须回传 `reasoning_content`。组合级厂商 `reasoning_effort`（官方 token）叠在聊天 / CEO / worker 上，后台 one-shot 仍关思考。

### 1.2 场景画像（ModelProfile）

单一事实源：每个用 LLM 的场景（chat / agent / memory / title）都是一个命名 profile（`ProfileParams`），持有采样参数；ReAct 路径另有可选 `max_rounds`（**0 = 无产品轮次顶**）。**model 与 profile 解耦**——turn 级 model 由 `TurnProfiles.model` 单点解析；调用点经 `model_selection`（`select_call` / `SelectedCall` + `build_selected_request`）**已统一装配**，不在业务侧直调 `profiles.build_request`。`select_for_scenario` 为预留配对，**未**进引擎热路径。

设计约束：
- profile 是**内部实现**，不暴露给 `delegate` 调用方；所有 worker 走同一 `agent` 画像（`agent_profile()` 无参、无 per-worker 档位）。
- `max_rounds` 仅 ReAct 路径（`engine.loop`）消费；`<=0` 表示无轮次保险丝（产品 `chat` / `agent` 默认）。一次性 `complete` 的场景取默认。显式正数只给测试筛 / CEO 手填短段 / 短修本段。

模型分配 / 思考开关分档 → [平台 LLM 接入](/docs/05-平台与运维/平台LLM接入.md)。

### 1.3 与其他模块的关系

→ 见代码：`apps/server/agentcore/llm/model_selection.py`（已统一策略入口：模型 × 请求参数）+ `llm/profiles.py`（场景 profile 表 / 底层 `build_request` 打包）+ `llm/resolve.py`（凭据解析）+ `llm/catalog.py`（上架/展示）。

## 三、沙箱执行（SandboxProvider）

→ 见代码：`apps/server/agentcore/tools/sandbox/`

### 3.1 实现：SubprocessSandbox / 云桌 GVisor

默认受限 subprocess 沙箱（非隔离边界，本机传统）；云端默认 `GVisorSandbox`（runsc）为 **每工作区长寿命 guest**（`tools/sandbox/gvisor.py`，Linux；紧急 `GVISOR_ENABLED=false`）。权威 → [安全 §三](/docs/05-平台与运维/安全权限与治理.md)。

**本机 subprocess**：临时目录 + `asyncio.wait_for` 超时 + stdout/stderr **2KB 分块异步捕获**（`on_output` 回调驱动 `tool_use_progress`）+ 执行后清理。桌面 `execute` 把同一回调接到 op 未结时的输出片段上（`workspace/exec_output.py`），结束后仍交整段结果。

**云桌 guest**：工作区 rw-bind、uid≡`app`、桌上 SSRF 出站（与 `web_fetch` 同政策）；用户态 = packed guest rootfs（不是 sandboxd `/usr`）；`execute` 为 `exec` 进已有 guest，不是每次 copy-in/out。流式输出同 `on_output`。

**否决**：裸 subprocess 云执行（无 SEC-005 ack）；普通路径再叠 copy-in/out 例外。

## 四、API 层（前端 ↔ 后端）

→ 见代码：`apps/server/agentcore/api/`（路由 + `schemas/`；挂载见 `main.py`；OpenAPI 为前端类型唯一真相源）

### 4.1 REST API

端点与请求/响应模型的唯一真相源是 FastAPI 路由 + 自动生成的 OpenAPI（前端类型由 `openapi-typescript` 生成；路径清单见 `paths.generated.ts`，手写 URL 由 `validate_rest_paths.py` 在 `pnpm gen:types` / CI contracts 门禁对齐）。

**新建会话的幂等键（✅）**：`POST /v1/conversations` 可选 `client_request_id`——客户端为「这一次发送」自铸一个 id，重试 / 重按复用同一个。同用户同键只建一条：第二次起原样返回首次那条（仍是 **201**、body 同形，**不**报 409）。并发同键靠 `(user_id, client_request_id)` 局部唯一索引裁决，输的那次回查首次那条返回。**省略该字段 = 旧行为**，一次请求一条，不拦不报错（老客户端照常工作）；服务端**不做**任何「同用户 / 同标题 / N 秒内」的启发式去重——只认显式键。同款模式见 IM 的 `chat_messages.client_msg_id`（[消息IM §二](/docs/05-平台与运维/消息IM.md)）。每次受理落 `conversation.created`（含 `idempotent_hit`），事件字段见 [对话日志分析指南](/docs/05-平台与运维/对话日志分析指南.md)。

> 认证路由详见 [`../05-平台与运维/认证与会话.md`](/docs/05-平台与运维/认证与会话.md)。

### 4.2 SSE 实时流

两种形态。**都要扇出**——差别在扇给谁：对话页的「对方」是服务端 AI、回复由 POST 造出，但同账号的第二台设备同样要看到（多端同权），扇出面是**你自己的各端**；消息页的「对方」是另一个人的客户端，扇出面是**对端的各端**。（旧口径「对话页 POST 即可造出回复、故无需扇出」只问了「回复从哪来」，没问「谁要看」——已作废。）

- **对话页（找 AI）**：`POST /v1/conversations/{id}/messages` **恒返回** `text/event-stream`（发送即有流）；第二台设备走 `GET /v1/conversations/{id}/stream?follow=true` 跟播（空闲会话也挂得住；同一回合可多端同时跟播）。请求体 ✅ **`delivery: "steer" | "queue"` 必填**（缺 → 422）。排队取消 `POST …/queued-turns/{queue_id}/cancel`。排队编辑 `POST …/queued-turns/{queue_id}/edit`（正文、附件、`@`；身份与顺序不动）。Steer / Queue / Stop 语义与已知行为 → [运行时三模型 · 同对话再发](/docs/03-AI核心/运行时三模型与挂起.md#同对话再发steer--queue)。封装见 `api/sse.py`；事件 → [SSE 事件与录制回放](/docs/03-AI核心/SSE事件与录制回放.md)。
- **消息页（找人 IM）**：每用户一条长连 firehose `GET /v1/realtime`（server→client），把别人发来的消息扇出到你的所有在线连接（多端）；发送仍走 `POST /v1/messages/chats/{id}/messages`。fan-out 进程内 pub/sub（`messaging/hub.py`）；跨进程扇出 ⏳ → [部署拓扑 · API 进程约束：多 worker 一律拒启](/docs/05-平台与运维/部署拓扑与环境.md#api-进程约束多-worker-一律拒启) · [消息 IM §四](/docs/05-平台与运维/消息IM.md)。事件信封 `{ type, ... }`，P0 类型 `chat_message`；Cookie 鉴权、断连按 `last_read_message_id` 拉增量补偿（best-effort，非持久投递）。

### 4.3 核心请求/响应模型

→ 见代码：`apps/server/agentcore/api/schemas/`（路由层做 ORM→Pydantic 映射；前端 TS 类型由 OpenAPI 自动生成）。

对话页 `GET /v1/conversations/{id}/messages` 的 `MessageDetail.agent_mentions` 回放用户 `@` 团队角色芯片（与 `attachments` 分列；软点名，非硬路由）。写路径见 `messages.agent_mentions` JSONB。本机回写 `POST …/local-turns` 的 `RecordTurnRequest.agent_mentions` 同列落库（可选；旧客户端省略）。活态投影另有 `POST …/local-turns/begin|heartbeat|journal|stream-segments` / `abort`（owner Bearer；终局仍 `POST …/local-turns`）→ [工作区](/docs/02-架构/工作区.md)。`GET …/queued-turns` 的 `QueuedTurnItem` 同步返回可选 `attachments` / `agent_mentions`（出队本就会转发给 `stream_chat`）。运行中插话 SSE `user_interjection.agent_mentions` 供插话气泡画角色芯片（可选加法）。

### 4.4 SSE 事件类型

SSE 事件契约不在此重复定义。事件信封为 `{ type, timestamp, payload }`，语义见 [SSE 事件与录制回放](/docs/03-AI核心/SSE事件与录制回放.md)。**TS 类型 SoT** = `packages/contract-types`（桌面 `types/events.ts` 仅 `export type *` re-export；后端产出事件见 `runtime/events/`）。

### 6.2 数据模型架构约定

单库 PostgreSQL、一个应用进程。行级引用由数据库约束守住；对象存储、浏览器会话、废公开链接这类跨聚合副作用留在服务里。事务边界 → [后端架构 §一、五层分层](/docs/02-架构/后端架构.md)。

#### 主键

主键统一 UUID（Python `str(uuid4())`）。

#### 引用完整性

插入时父行已经在的引用，声明 `ForeignKey`。

| 关系 | 删除 |
|------|------|
| 组合：子行离开父行没有独立意义（消息、偏好、文件夹成员、排队、公告已读、创作稿、桌面设定） | `ON DELETE CASCADE` |
| 对话归属 `conversations.folder_id` | `ON DELETE RESTRICT`。软删文件夹行还在。保留期清扫先解开归属；彻底删除先硬删成员对话 |
| 裸聊指针 `conversations.auto_desk_folder_id` | `ON DELETE SET NULL`。对话留下。软删时行还在，服务仍把指针清空 |
| 已撤销分享的父指针 `conversation_shares.conversation_id`、`doc_shares.doc_id` | `ON DELETE SET NULL`。行和快照留下。撤销（`revoked_at`）仍在服务里 |
| 多维表格的行和视图 `table_rows.table_id`、`table_views.table_id` | `ON DELETE CASCADE`。软删表时行还在 |
| 表格绑定的对话 `tables.conversation_id`、当前视图 `tables.active_view_id` | `ON DELETE SET NULL`。表留下 |
| 找人会话的成员和消息 `chat_members.chat_id`、`chat_messages.chat_id` | `ON DELETE CASCADE` |
| 已读游标 `chat_members.last_read_message_id`、回复指针 `chat_messages.reply_to_message_id` | `ON DELETE SET NULL`。撤回不清行，指针留着 |
| 技能货架的版本、安装、举报，以及安装指向的版本和本机文稿 | `ON DELETE CASCADE`。本机技能正文在另一行，不跟着货架行消失。软删文稿时行还在，服务仍按「文稿没了即卸载」清安装 |
| 货架当前版本 `skill_store_listings.current_version_id`、上架源 `skill_store_listings.source_document_id` | `ON DELETE SET NULL`。版本快照留下。再发布仍要活的源文稿 |
| 交接任务 `handoff_jobs.source_conversation_id`、`handoff_jobs.job_conversation_id` | `ON DELETE CASCADE`。软删对话行还在。任一端硬删带走任务行。任务不是账本 |
| 账本 `cost_events` / `cost_calls` | 不级联。账号注销保留账本。对话硬删若要拆掉对应行，由那条删除路径显式删 |
| `documents.parent_id` | 仍是裸列。自引用 `RESTRICT` 会卡住文件夹一次删掉父子；`CASCADE` 会把别的作用域里挂在这个节点下的子行一起删掉 |
| 各表 `user_id`、模型组合指针 | 仍是裸列。注销不删账号行。预设 id 和平台 / 自带密钥不是同一张父表 |
| `turn_journal.turn_id`、挂起帧的 `message_id` | 不外键到 `messages`。事实可以先于投影行写入。`conversation_id` 在对话已存在时指向 `conversations`，硬删用 `CASCADE` |
| 头像对象、浏览器会话 | 留在应用服务 |

现状：组合外键已落地，`ON DELETE CASCADE`。对话子行：`messages`、`conversation_preferences`、`turn_queue_items`、`turn_journal`、`paused_turns`、`paused_turn_outcomes`、`turn_leases`、`run_sessions`、`memory_updates`、`conversation_external_grants`、`agent_audit_events`。文件夹：`folder_members.folder_id`、`docs.folder_id`、`documents.folder_id`（空的 `folder_id` 是账号级，不指向文件夹）。对话归属 `conversations.folder_id` 是 `ON DELETE RESTRICT`；裸聊指针 `conversations.auto_desk_folder_id`、分享父指针 `conversation_shares.conversation_id` 与 `doc_shares.doc_id` 是 `ON DELETE SET NULL`。公告已读：`product_notice_dismissals.notice_id`。对话硬删只再显式删 `turn_stream_state`（没有 `conversation_id`）和对话范围的账本行。文件夹彻底删除先撤销文档公开链接、硬删成员对话，再删文件夹行；自动云桌指针随文件夹行置空。账本不级联。多维表格的行和视图、找人会话的成员和消息、技能货架的版本 / 安装 / 举报、交接任务，都随父行级联。表格绑定的对话和当前视图、货架当前版本和上架源，父行没了只置空。`documents.parent_id`、各表 `user_id`、模型组合指针仍是裸列。没点名的 `*_id` 仍是裸列。新表按上表写；补外键前先处理父行已经不在的子行。

否决「全库不建外键」。单库里这不会换来松耦合，只会把组合关系拆成多份手写删除清单。

#### 软删除

带 `deleted_at` 的表，活数据查询自己写 `deleted_at IS NULL`。回收站和保留期清扫显式查墓碑。活行唯一性用部分唯一索引（`WHERE deleted_at IS NULL`）。

否决全局 ORM 监听器自动滤掉已删行：没落地，加上之后回收站、清扫和裸 SQL 会各看各的。

#### 聚合与删除

一个聚合根一次删干净。对话硬删只再写 `turn_stream_state` 和对话范围的账本；其余组合行由 `ON DELETE CASCADE` 带走。文件夹彻底删除先撤销文档公开链接并硬删成员对话，成员、创作稿和该桌设定随文件夹行级联，自动云桌指针置空。归属还在时，文件夹行删不掉。保留期清扫先解开归属。分享行留下，父行消失时指针置空；撤销仍在服务里。多维表格硬删带走行和视图，绑定的对话和当前视图只置空。找人会话硬删带走成员和消息。技能上架行带走版本、安装和举报；上架源文稿没了只把指针置空，本机文稿硬删卸掉对应安装。交接任务在任一端对话硬删时一起删。账号注销仍是一份清单。盘上文件留在服务里。

`documents`（规则 / 记忆树）和 `docs`（创作稿）是两个聚合，都留。

#### 文件模型单表设计

文件系统采用单表 + 维度收敛设计（`kind` × `role`），不拆多张领域表——单表是「文件夹 = 上下文边界、一棵树什么都能放」的物理基础。拆表会打碎统一内容树。

| 维度 | 含义 |
|------|------|
| `kind` | 节点类型（folder / document / upload / base），DB CheckConstraint |
| `role` | AI 上下文角色（rule / general / attachment 等）；`rule` 由 `ai_maintained` 区分用户规则与存量笔记。该字段留 DB、不进 prompt，只服务写侧防护。→ [记忆 · 用户规则](/docs/03-AI核心/Agent记忆与知识系统.md#用户规则) |

非树资产（头像等）剥离到独立 asset 模块（不在树、无 parent_id 语义）。

版本不另起 `agent_versions` / `file_versions`。Agent 不上架（§6.3）。规则正文用内容哈希 CAS；创作稿用 `docs.version`。

#### JSONB 策略

JSONB 列不盲加 GIN 索引。真正的扩展杠杆是「先用高选择性主键/外键列限定作用域 + 应用层分页」。复查触发条件：单作用域记录到万级、出现跨作用域 JSONB 查询、或特定操作符成为高频慢查询。

#### ORM 是 Schema 真相源

全部表由 Alembic 迁移链维护；以 Alembic head 为准。冷启动 = `alembic upgrade head`（建 schema）+ seed（灌初始数据），职责分离。默认值一律用 `server_default`（数据库级）。

#### 索引策略

索引随 ORM 列定义一并维护。
